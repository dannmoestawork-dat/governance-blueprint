## Why this file exists

Two functions, one file.

1. **Recurring maintenance.** Some tasks need to happen on a cadence
   — security scans, memory index review, inventory spot-checks —
   not because they're urgent, but because skipping them silently
   degrades the system. The checklist with last-run dates makes
   "I haven't done this in two months" visible *before* it bites.

2. **Context evolution log.** When the operator adds new memory
   files, KM entries, governance updates, protocol changes, tool
   integrations — capture *what* was added and *why*. This is the
   changelog for how the AI partnership grows. Future-you (and future-
   agents) read this to understand how decisions accumulated.

   ("KM" = Knowledge Management — the directory where *validated*
   processes live, distinct from feedback memories and per-tool
   MAINTENANCE_LOGs. See `LLMP001_..._KNOWLEDGE_MANAGEMENT.md` for
   the full layer; in this doc you'll see KM mentioned as one of the
   sources of context-evolution-log entries.)

## How to use it

- **Agent at session start:** check the recurring-maintenance checklist;
  surface anything overdue (per `SESSION_PROTOCOL.md` §5).
- **Agent during session:** add a context-evolution entry when creating
  or updating memory files, KM entries, protocol changes, or governance
  documents.
- **Operator anytime:** browse the evolution log to see how the system
  has matured. Each entry is a potential talking point for content,
  CE materials, or onboarding new collaborators.

## Recurring Maintenance Checklist

Standing tasks with cadence and last-run tracking. The agent checks
these at session start.

| Item | Cadence | Last Run | Next Due |
|---|---|---|---|
| Secrets / credentials scan | Weekly | YYYY-MM-DD | YYYY-MM-DD |
| Full security scan | Monthly | YYYY-MM-DD | YYYY-MM-DD |
| MEMORY.md line count check (<200) | Every session | YYYY-MM-DD | next session |
| Memory index review (descriptions, staleness) | Monthly | YYYY-MM-DD | YYYY-MM-DD |
| LEARNING_LOG active corrections review | Monthly | YYYY-MM-DD | YYYY-MM-DD |
| INVENTORY.md accuracy spot-check | Monthly | YYYY-MM-DD | YYYY-MM-DD |
| TASK_QUEUE.md stale `[>]` items | Biweekly | YYYY-MM-DD | YYYY-MM-DD |
| KNOWN_LIMITATIONS.md re-read | Quarterly | YYYY-MM-DD | YYYY-MM-DD |
| Per-tool MAINTENANCE_LOG sync (any drift?) | Quarterly | YYYY-MM-DD | YYYY-MM-DD |
| Folder layout vs. FOLDER_LAYOUT.md drift check | Quarterly | YYYY-MM-DD | YYYY-MM-DD |

**Adapt this list to your domain.** Some items may not apply (e.g.,
no secrets to scan if your tools have no credentials yet); others may
need adding (e.g., backup verification, license compliance review,
external service health check).

**Cadence rule of thumb:**
- *Weekly:* high-frequency, low-effort. The kind of thing that, if
  skipped for a month, costs hours to recover.
- *Monthly:* medium-frequency, medium-effort. Periodic hygiene that
  keeps the system from rotting.
- *Quarterly:* low-frequency, high-effort. Strategic re-reads and
  audits that catch slow drift.

## Context Evolution Log

Add entries chronologically (newest first). Each entry is a session-
worth of significant changes. Skip routine work — reserve entries for
new infrastructure, new patterns, or load-bearing decisions.

### Template

```markdown
### YYYY-MM-DD — [Short title for the session]

[2-4 sentence summary of what changed and why.]

- **What changed (1):** [thing 1, with paths/files]
- **What changed (2):** [thing 2]
- **Why:** [the trigger or motivation]
- **New memories saved:** [list any new topic files]
- **Files affected (new):** [paths]
- **Files affected (updated):** [paths]
- **Lessons:** [1-3 numbered lessons from the session]
- **(Optional) Public link:** [if this becomes a podcast/article topic, note it]
```

---

### YYYY-MM-DD — [Example entry]

[Single long session that established the recurring-maintenance
checklist + did the first inventory spot-check. The check surfaced
two stale entries — both deprecated tools that hadn't been removed.]

- **What changed (1):** Added recurring-maintenance checklist to
  `SESSION_ENV.md` with 8 items at three cadences.
- **What changed (2):** First monthly inventory spot-check done;
  removed 2 deprecated tools from `INVENTORY.md`; updated 1 path
  that had shifted in last month's reorg.
- **Why:** Cadence drift was already showing — last security scan
  was 47 days ago; memory index hadn't been reviewed since
  inception.
- **New memories saved:** None (process change, not knowledge).
- **Files affected (updated):** `SESSION_ENV.md`, `INVENTORY.md`.
- **Lessons:**
  1. The cadence list itself becomes the forcing function. Without
     last-run dates, the schedule is invisible.
  2. Inventory drift is silent. The spot-check found drift that
     would have grown.
  3. Quarterly cadence on KNOWN_LIMITATIONS.md re-read is
     load-bearing — that doc is where we capture what's still
     broken, and it's the easiest thing to forget.

## Why one file, not two

The recurring-maintenance checklist and the context-evolution log
could be separate files. They aren't, deliberately:

- The checklist surfaces the *same kind of work* the log records —
  routine hygiene that compounds.
- One file means one thing to read at session start.
- Cross-references between the two (e.g., "ran the security scan,
  here's the entry") stay tight when they're in the same doc.

If the file gets unwieldy (~1000+ lines), the natural split is:
extract older log entries to a dated archive (`SESSION_ENV_2025.md`,
etc.). Keep the checklist + most recent 3-6 months in this file.

## Maintenance

- **Every session:** check the recurring-maintenance table; update
  `Last Run` for anything completed.
- **At significant milestones:** write an evolution log entry.
- **Quarterly:** review the cadence list — is it still right? Add /
  remove items as the system matures.

## What NOT to put here

- **Conversation summaries.** → not durable enough; goes in chat or
  task notes.
- **Per-tool decision logs.** → that tool's `MAINTENANCE_LOG.md`.
- **Open questions to the operator.** → `TASK_QUEUE.md`.
- **Operator profile / preferences.** → `MEMORY.md` user-type
  topic files.
