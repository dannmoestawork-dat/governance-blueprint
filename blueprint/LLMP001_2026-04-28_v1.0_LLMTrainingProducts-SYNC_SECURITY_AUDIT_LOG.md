## Why this file exists

Three reasons.

1. **Cadence enforcement.** Without a logged history, "I last scanned
   in [recent month]" becomes "I last scanned six months ago" without
   you noticing. The log makes drift visible.
2. **Trust trail.** When someone asks "is this vault clean?" you have
   an answer with dates and findings, not a guess.
3. **Pattern detection.** If the same finding keeps recurring, the
   *fix* isn't the issue — the *process* is. The log surfaces that.

---

## What gets scanned

The specific scans depend on your stack. Common categories:

| Category | What it checks for | Why it matters |
|---|---|---|
| Secrets | API keys, passwords, tokens hardcoded in files | Easiest leak; biggest blast radius |
| Credentials in repos | `.env` files, `*.pem`, `*.key` accidentally committed | Same as above, distributed |
| Permissions | Files / dirs with overly-permissive ACLs (e.g., 777) | Lateral access if machine is compromised |
| Cloud-sync exposure | Anything in OneDrive/iCloud/Dropbox marked Tier 4–5 | Trust gap if sync provider doesn't meet your bar |
| Outdated dependencies | Pinned packages with known CVEs | Code execution risk |
| Open ports / services | Local services accepting connections | Attack surface |
| `git log` for secret-shaped strings | High-entropy strings in commit history | Git history is forever |
| External account audit | Accounts with credentials in your vault | Exposure if vault leaks |

**Adapt to your stack.** A solo operator doing local-only knowledge
work may skip ports and CVEs but emphasize secrets and cloud-sync.
A team running production services adds CI checks, image scans,
cloud-account audits.

## Cadence

Standing recommendation:

| Scan | Cadence | Notes |
|---|---|---|
| Secrets / credentials scan | Weekly | Cheap; catches accidents fast |
| Full audit (all categories) | Monthly | First session of each month |
| Pre-deployment review | On demand | Before any tool goes external |
| Quarterly deep audit | Quarterly | Includes vault inventory + classification spot-check |

Cadence dates live in `SESSION_ENV.md`'s recurring-maintenance
checklist. Scan results live here.

## What scans look like (suggested capabilities)

Your scan tool should at minimum:

- **Find high-entropy strings.** API keys, tokens, base64-looking
  blobs. Regex + entropy threshold catches most.
- **Find filenames matching credential patterns.** `*.pem`, `*.key`,
  `id_rsa`, `*.p12`, `credentials.json`, `.env` (without `.example`).
- **Check git-tracked paths.** Anything matching the above that's
  tracked by git is high-priority.
- **Classify by location.** A `.env` in a cloud-synced dir is worse
  than a `.env` in a local-only dir.
- **Output structured.** Markdown table or JSON. The log entry copies
  from the output; if your output is a wall of text, logging is
  painful and gets skipped.

Tools that exist (pick based on stack):
- `gitleaks` — git-history secret scanner
- `trufflehog` — high-entropy + regex secret scanner
- `bandit` — Python static analysis (security-focused)
- Custom scripts — for project-specific checks
  (cloud-sync exposure, classification consistency, etc.)

## Approved security patterns

When a scan finds a problem and the operator approves a *pattern*
(not just an instance) for resolution — log the pattern in a
separate file (e.g., `Knowledge_Management/approved_security_patterns.md`).

The audit log records the *findings*. The pattern file records the
*decisions* that govern future findings. They cross-reference:

- Audit log entry says: "Resolution: per pattern PSP-003 — see
  approved_security_patterns.md."
- Pattern file says: "PSP-003: any `.env` file with API keys must
  live outside cloud-sync. Created YYYY-MM-DD in response to audit
  finding [link]."

## What NOT to log here

- **Code-vulnerability fixes** that aren't security-related. Bug
  fixes go in the relevant tool's `MAINTENANCE_LOG.md`.
- **Conversation about security** without a scan run. The log is for
  scans + findings, not abstract discussion.
- **One-off "I checked X manually."** Either run it as a repeatable
  scan or note it in TASK_QUEUE and skip the log.

---

## Maintenance

- **Every scan:** add an entry. Don't batch.
- **Monthly:** review the previous month's log. Are findings
  recurring? Is the cadence honored? Update `SESSION_ENV.md` if drift
  is showing.
- **Quarterly:** re-read approved patterns. Are any obsolete? Should
  any be tightened?
