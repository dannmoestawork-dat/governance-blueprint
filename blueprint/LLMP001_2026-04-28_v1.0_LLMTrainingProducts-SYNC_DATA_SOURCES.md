## Why a data-sources doc

Two reasons.

1. **Discoverability.** Without this index, the agent (and future-you)
   doesn't know what's available. It re-asks for inputs you already
   have, or fabricates plausible-but-wrong data.
2. **Handling rules.** Different sources have different rules — some
   are read-only, some are licensed, some require credential management,
   some are sensitive. Putting handling rules next to source pointers
   means the rules actually get followed.

The exact tables below are placeholders. Adapt them to your domain.

```markdown

|---|---|---|---|

```

Common section breakdowns (pick what fits):

- **Internal reference data** — files in your vault that other
  tools consume.
- **Vendor / supplier data** — proprietary data from partners,
  may be licensed.
- **Approved external sources** — public-source data your tools can
  pull from (with attribution as needed).
- **Internal sensitive data** — pricing, financials, anything
  Tier 4–Tier 5.
- **Project-specific document repositories** — where work product
  for active engagements lives.
- **System / hardware references** — hardware build docs, infra
  configs.

## Handling rules

Standing rules that apply to every source in the index. Adapt as
needed but don't drop the spirit.

### For all sources
- **Read-only.** Never modify originals. Extract zips to a temp
  directory; don't extract in place.
- **Cross-reference required.** All claims must be verifiable against
  source data. If it can't be cited, don't say it.
- **Synthesis is the goal.** Raw data is input, not output. It feeds
  tools and deliverables.

### For vendor / proprietary sources
- May be **proprietary but not secret** — published to authorized
  parties. Reference in deliverables; don't republish in a competing
  product.
- Verify the source is still accessible before depending on it.
- Note credential requirements (some sources require logins or API keys).

### For sensitive / Tier-5 data
- **Never include in external-facing output without explicit operator
  approval** (see `GOVERNANCE.md` §6a — Classification Downgrade Gate).
- Live in a designated directory. Don't scatter.
- Excluded from cloud-sync if the sync provider doesn't meet your trust
  threshold.

### For public-source data
- **Verify the source is still accessible** before building a tool that
  depends on it.
- Note login requirements (some "public" data requires accounts).
- Public-source URLs change. Log working URLs when found; expect
  breakage; have a fallback plan.

## Adding new sources

When you onboard a new source, walk through the checklist:

### New vendor / supplier
1. Create directory: `[your_vault]/Reference/[Vendor]_Data/`
2. Add entry to the appropriate category table above.
3. Store raw data (specs, drawings, product sheets) — read-only.
4. Update `INVENTORY.md` if a tool is built to process it.
5. Note licensing/redistribution constraints if any.

### New external source
1. Add to the appropriate category table above.
2. Note access method (public, login, licensed).
3. If it feeds a tool, document the dependency in that tool's
   `MAINTENANCE_LOG.md`.

### New project documents
1. Place in the appropriate project directory (not a top-level
   reference area unless they're general reference).
2. Project-specific bid docs / drawings / specs → the project's
   folder.
3. General reference (manuals, regulations, codes) → reference area.

## Why "data sources" is one document

Could be split into per-domain files. Doesn't, deliberately.

A single index is greppable, scannable, and survives folder
reorganization better than scattered per-folder READMEs. When the
index gets big enough that one file is unwieldy (~500+ rows), split
by category — but keep this file as the top-level pointer to the
splits.

## Maintenance

When to update this file:
- New data source onboarded.
- Existing source deprecated, moved, or status changes.
- Access method changes (URL change, licensing change, credentials).

When NOT to update:
- Routine additions of *content* within an existing source's
  directory.

Who updates: agent during a session (when a new source is referenced),
or operator between sessions when planning new work.
