# MEMORY_SCHEMA.md — Persistent Cross-Session Memory Architecture
## Classification: Tier 4 (internal — operator + agent)
## [AI-GENERATED] — 2026-04-28 — Apache 2.0
## Part of: LLM Training Products v1.0

> **Purpose.** Define the file-based memory system that survives across
> conversations — the difference between "a clever assistant" and "a
> colleague who remembers." This is the schema, the index pattern, the
> four memory types, and the rules for when to write, when to read, and
> when to forget.

---

## Why memory matters

LLM context windows are large (200K, 1M, 10M tokens) but **finite and
ephemeral**. Every new conversation starts fresh — no recollection of
prior work, prior decisions, prior corrections. Without persistent
memory, every session is "groundhog day": you re-explain who you are,
re-state your preferences, re-correct the same mistakes.

**Persistent memory** lives outside the context window — on the
filesystem, as plain markdown files — and gets selectively re-loaded at
the start of each conversation. The agent reads what's relevant, ignores
what isn't, and updates the store as new things are learned.

Memory is **not the same as** the conversation history. Conversation
history is "what we said this turn." Memory is "what's still true across
turns and across sessions."

## The schema — at a glance

```
<memory_root>/
├── MEMORY.md                              ← Index file (always loaded — under 200 lines)
│
├── user_<topic>.md                        ← Operator profile
├── feedback_<topic>.md                    ← Behavioral guidance
├── project_<topic>.md                     ← Active project context
├── reference_<topic>.md                   ← External-resource pointers
└── domain_<topic>.md                      ← (optional) domain-knowledge anchors
```

**`MEMORY.md`** — the index. Always loaded into the agent's context at
session start. Lists every topic file with a one-line description.

**`<topic>.md`** — individual memory files. Each one is small, focused,
and carries frontmatter. Loaded only when the topic is relevant.

## The four memory types

### 1. `user` memories

**Purpose.** Information about the operator — role, goals, responsibilities,
knowledge level, working preferences. Helps the agent tailor its behavior.

**When to save.** When you learn details about the operator's role,
preferences, responsibilities, or domain knowledge.

**How the agent uses it.** When tasks should be informed by the operator's
profile or perspective. (Explaining code differently to a senior engineer
vs. a beginner; using domain vocabulary the operator already knows.)

**Examples:**
- "Operator is a research scientist focused on observability/logging in
  data pipelines."
- "Ten years of Python; first time touching this project's frontend —
  frame frontend explanations in terms of backend analogues."

### 2. `feedback` memories

**Purpose.** Guidance the operator has given about how to approach work —
both what to avoid and what to keep doing.

**When to save.** Any time the operator corrects ("don't do X") OR confirms
a non-obvious approach worked ("yes, exactly, keep doing that"). Save the
*why* alongside the rule so the agent can judge edge cases later.

**How the agent uses it.** Lets the agent stay coherent and responsive
without needing the same correction twice.

**Body structure (load-bearing):**
- **Rule:** Lead with the rule itself.
- **Why:** The reason the operator gave (often a past incident or strong preference).
- **How to apply:** When/where this guidance kicks in.

**Examples:**
- "Don't mock the database in integration tests — we got burned last
  quarter when mocked tests passed but the prod migration failed."
  - *Why:* prior incident where mock/prod divergence masked a broken migration.
  - *How to apply:* every time integration tests are being written.
- "For refactors in this area, prefer one bundled PR over many small ones."
  - *Why:* operator confirmed this approach reduces churn.
  - *How to apply:* when assessing PR-splitting strategy in this module.

### 3. `project` memories

**Purpose.** Information about ongoing work, goals, initiatives, bugs, or
incidents that is **not derivable from the code or git history**. The
broader context behind the work.

**When to save.** When you learn who's doing what, why, or by when. Convert
relative dates to absolute dates ("Thursday" → "2026-03-05") so the
memory remains interpretable later.

**How the agent uses it.** To make better-informed suggestions and
understand the *motivation* behind requests.

**Body structure:**
- **Fact / decision** first.
- **Why:** the motivation (constraint, deadline, stakeholder ask).
- **How to apply:** how this should shape suggestions.

**Examples:**
- "Merge freeze begins 2026-03-05 for mobile release cut. Flag any
  non-critical PR work scheduled after that date."
- "Auth middleware rewrite is driven by legal/compliance requirements
  around session token storage, not tech-debt cleanup. Scope decisions
  should favor compliance over ergonomics."

### 4. `reference` memories

**Purpose.** Pointers to where information lives in **external systems**
(Linear, Slack, Grafana, internal wikis).

**When to save.** When you learn about external resources and their
purpose. ("Bugs are tracked in Linear project X." "The on-call dashboard
lives at Y.")

**How the agent uses it.** When the operator references an external
system or when up-to-date information might be there.

**Examples:**
- "Pipeline bugs are tracked in Linear project `INGEST`."
- "`grafana.internal/d/api-latency` is the on-call latency dashboard —
  check it when editing request-path code."

### Optional: `domain` memories

For long-lived domain-knowledge anchors that aren't quite project context
but aren't quite operator profile either. Use sparingly — most domain
knowledge should live in `Reference/` directories or per-project docs,
not in cross-session memory.

## Frontmatter — required for every topic file

```markdown
---
name: {{memory name}}
description: {{one-line description — used to decide relevance in future
              conversations, so be specific}}
type: {{user, feedback, project, reference, domain}}
---

{{memory content — for feedback/project types, structure as: rule/fact,
then **Why:** and **How to apply:** lines}}
```

The `description` field is what the agent sees when scanning the index.
**Be specific.** "Background tasks" is too vague. "Never sign off with
background tasks running — they orphan and don't surface errors" is what
lets the agent decide whether to load the memory.

## The index — `MEMORY.md`

`MEMORY.md` is the **always-loaded** entry point. It is an index, not a
memory. Each entry is one line, under ~150 characters:

```markdown
- [Title](file.md) — one-line hook
```

**Hard rules:**
- No frontmatter on `MEMORY.md` itself (it's an index, not a memory).
- Never write memory content directly into `MEMORY.md` — only pointers.
- Keep the index under 200 lines (auto-load truncation limit on most
  harnesses).
- Organize semantically by topic, not chronologically.

**Soft rules:**
- Group entries by type (user, feedback, project, reference) when the
  list grows beyond ~20 entries.
- Keep one-line hooks specific enough to skim — vague hooks make the
  agent open every file. **This is a real token-saving opportunity:**
  every unnecessary topic-file load costs tokens at the moment of
  loading, and tight hooks let the agent decide relevance from the
  index alone. Vague memory descriptions tax every future session.

## When to read memory

- When memories seem relevant to the current task.
- When the operator references prior-conversation work ("remember when we...").
- When the operator explicitly asks to check, recall, or remember.

**When to NOT use memory:**
- Operator says "ignore memory" or "don't apply remembered facts."
- Memory record contradicts current observable code/state — trust what
  you observe now and update the stale memory.

## When to write memory

| Situation                                             | Save?                                                              | Type               |
| ----------------------------------------------------- | ------------------------------------------------------------------ | ------------------ |
| Operator corrects your approach                       | Yes                                                                | feedback           |
| Operator confirms a non-obvious choice worked         | Yes                                                                | feedback           |
| Operator says "remember this"                         | Yes                                                                | depends on content |
| You learn the operator's role, expertise, preferences | Yes                                                                | user               |
| You learn about an external system / where data lives | Yes                                                                | reference          |
| You learn about an in-flight project's *motivation*   | Yes                                                                | project            |
| You finished writing some code                        | **No** — code is its own record                                    |                    |
| You learned a code pattern by reading the code        | **No** — derive on demand                                          |                    |
| You found a bug                                       | **No** — the fix is in the code; the commit message is the durable record | (a "git moment" — git, not memory) |
| Routine task completion                               | **No**                                                             |                    |
| Conversation summary                                  | **No** — that's what session-end notes are for                     |                    |

## What NOT to save (even if asked)

These exclusions hold even when the operator explicitly says "save this":

- **Code patterns, conventions, architecture, file paths.** Derivable by
  reading the project state.
- **Git history, recent changes, who-changed-what.** `git log` / `git
  blame` are authoritative.
- **Debugging solutions or fix recipes.** The fix is in the code; the
  commit message has the context.
- **Anything already documented in the directive (DIRECTIVE.md).**
- **Ephemeral task details.** In-progress work, temporary state, current
  conversation context.

If the operator asks you to save a list of recent activity or a PR
summary, gently redirect: *what was surprising or non-obvious about it?*
That's the part worth keeping.

**Exception — operator testing the schema.** When the operator is
deliberately probing the agent's process, memory rules, or onboarding
behavior (during system build, audit, training of a new collaborator,
or methodology review), they may ask the agent to save things that
would normally be redirected. In testing context: state the redirect
rule out loud so the operator sees the boundary the rule enforces, then
honor the explicit request. Don't silently override; don't silently
comply. The point of the test is to surface the rule, not to bypass it.

## When to update or forget

- **When a memory turns out to be wrong:** update the file. Don't leave
  contradictory state.
- **When a memory is outdated:** *capture history before deletion.*
  Before deleting, record what the memory said, when it was true, why
  it's now stale, and what supersedes it. Either move the prior content
  to `ARCHIVE.md` per the deletion-protocol pattern, or note the
  supersession at the top of the new memory's body. *Then* delete the
  file and the index pointer. **Wrong memory is worse than no memory;
  unrecorded deletion of memory is also a loss.** Both ends matter.
- **When the operator says "forget that":** **first, confirm WHAT.**
  "Forget that" is ambiguous; the agent must restate exactly which
  memory entry it's about to delete and wait for explicit confirmation
  before acting. Once confirmed, capture history per the rule above,
  delete the file, remove the index pointer. **The wrong deletion is
  irreversible — confirmation is the only safety.**

**Memory ages.** A memory written 6 months ago that says "we're using
PostgreSQL 14" may be wrong now. Use memory as *context as of the time
written*. Before recommending action based on memory:

- If the memory names a file path: check the file exists.
- If it names a function, flag, or string: **search the codebase for it.**
  Use your editor's project-wide search, or `grep` / `rg` from the terminal
  — the goal is to find every place the named thing appears so you can
  verify the memory still describes reality. ("Grep" is a Unix-tradition
  command-line search tool; "ripgrep" / `rg` is its modern equivalent. If
  you don't use a terminal, your editor's "Find in All Files" does the
  same job.)
- If the operator is about to act on your recommendation: verify first.

"The memory says X exists" is not the same as "X exists now."

## Memory vs. other forms of persistence

Memory is one of several persistence mechanisms. Use the right one:

| Mechanism | Lives | Use for |
|---|---|---|
| Conversation context | This session | What we just discussed |
| Plan / approach | This session | Multi-step proposed work being aligned |
| Task list | This session | In-progress sub-tasks |
| Memory | Across sessions | Stable facts useful in future conversations |
| `MAINTENANCE_LOG.md` | Per-tool, durable | Tool-specific decision history |
| `KM/` (knowledge management) | Cross-session, validated | Carved-in-stone processes |
| Code | Forever | Behavior |

**Plans are not memory.** If you're aligning on a non-trivial implementation
approach, use a plan. Don't write the plan to memory.

**Tasks are not memory.** If you're breaking work into discrete steps,
use a task list. Don't write the task list to memory.

## Curation — the two-part discipline

Memory needs *active maintenance*, not just write-only growth.

1. **Create as many sub-memory files as needed** to maintain context.
   Don't cram unrelated topics into one file just to keep file count down.
2. **Improve memory processes when context is lost.** If a reference
   doesn't truly follow to its target, fix the link. If an inference
   lacks logic, fix the source memory or remove it. If a memory is
   stale, refresh or delete.
3. **Confirm all chains to root remain intact.** Every memory should
   trace back to a load-bearing principle, document, or established
   pattern — its *root*. Over time:
   - The number of intermediate steps in a chain may change.
   - The context at each step may be refined.
   - **But there should be no gaps between any memory and its root.**
   When you find a gap (a reference that no longer resolves, an
   inference whose justification has been deleted, a pointer to a
   doc that's been split or moved), fix it. Don't leave dangling
   chains.

This is the curation loop: write → use → notice failure → fix → repeat.

## Token economics

Every auto-loaded file is paid for at every conversation turn. `MEMORY.md`
is auto-loaded — keep it lean.

**"Topic files" are the individual memory files** — every
`feedback_<topic>.md`, `project_<topic>.md`, `user_<topic>.md`,
`reference_<topic>.md`, and (optionally) `domain_<topic>.md` in your
memory directory. Each one is "about one topic." These are loaded *only
when the agent decides they're relevant* to the current task — so they're
effectively free in tokens until they're used.

The vault you're already running uses topic files heavily; the term
"topic file" is just the name we give to the *individual memory file*
when contrasting it with the always-loaded *index* (`MEMORY.md`). Same
mechanism, sharper vocabulary.

**Implication:** Push detail into topic files. Keep the index tight.
A bloated `MEMORY.md` is a permanent tax on every conversation; a
bloated topic file costs nothing until needed.

## Worked example — a memory file

```markdown
---
name: Pre-task approval briefs
description: Operator wants approval briefs in plain language before any task >5 min
type: feedback
---

# Pre-task approval briefs

**Rule:** Before starting any task estimated to take more than 5 minutes,
send the operator a plain-language brief: scope, approach, success criteria,
estimated time. Wait for approval ("go", "do it", "approved") before
beginning execution.

**Why:** Operator was burned several times by long autonomous runs that
went sideways early — by the time they checked in, an hour of work was
on the wrong track. The approval brief catches bad plans before
implementation.

**How to apply:**
- Quick lookups, file reads, simple edits → no brief needed.
- Anything involving multi-file changes, scripts to run, web fetches,
  or research → brief first.
- The brief itself takes 30 seconds to write and the operator usually
  approves within a minute. Cheap insurance.
```

This is the structure: frontmatter at top, rule prominent, why-and-how
follow. Future-the-agent reads this and knows both *what* the rule is
and *when* to apply it.

## Adoption checklist

To set up memory in a new vault:

1. Create the memory directory (path varies by harness — for Claude
   Code, it's auto-managed under `~/.claude/projects/<...>/memory/`).
2. Create empty `MEMORY.md` with the section headers you'll use
   (e.g., `## User Profile`, `## Active Projects`, `## Memory Index`).
3. Add a Section 9 to your `DIRECTIVE.md` (Session Memory Protocol)
   pointing the agent at the memory directory.
4. As you work, save memories one at a time. Don't try to seed it in
   bulk — let it grow organically.
5. Curate every few weeks: re-read `MEMORY.md`, prune what's stale,
   tighten what's vague.
