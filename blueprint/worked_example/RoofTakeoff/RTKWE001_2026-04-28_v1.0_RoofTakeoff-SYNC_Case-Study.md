## Setup

A specialist operator (an independent practitioner in a regulated
field) needed to measure complex physical structures from construction
drawings. Each project required hours of manual measurement that fed
downstream cost calculations. Errors compound; a 5% error on a
10,000-unit job produces a meaningfully wrong number.

The operator had:
- A vault organized per `FOLDER_LAYOUT.md` (production / pipeline /
  reference / tools split).
- A directive (per `DIRECTIVE.md`) anchoring identity and standing rules.
- A nascent memory store with ~30 topic files.
- A standing 3-tier task model.

The agent in the partnership: a frontier model accessed via a CLI
agent harness. The operator kept the methodology vault on cloud sync
(`SYNC` tag). No air-gapped infrastructure yet.

## 1. Session 1 — From idea to v1.0 (~4 hours)

### What the operator brought

A morning chat: "I want to measure roofs from PDF drawings without
spending all day on a tape measure and a calculator. The drawings
have all the info; I just need a faster path."

### What the agent did first

Per the directive's working-style section: "Propose your approach in
plain language before writing code." The agent did not start coding.
The agent asked four questions:

1. What does the source PDF actually contain? Vector geometry, raster,
   both?
2. Can the operator add color marks to a rendered image (the way you'd
   highlight a printed page)?
3. What's the operator's tolerance for error — is 5% acceptable, or
   does this need to be within 1%?
4. What does "done" look like — a single number, or a structured
   data file?

Two of the answers shaped the whole tool:

- *PDFs are stamped scans of vector drawings; vector text-extraction
  finds the wrong things (callouts, not symbols).* The agent
  determined that **pixel-detection on a human-annotated rendering**
  would be more reliable than vector parsing.
- *5% is way too loose; the operator needs ~1% on the bbox.* That
  shifted the design toward a calibration-line scheme: the operator
  draws one line of known length, the script computes the pixel-to-real
  ratio.

### The plain-language proposal

The agent wrote a 200-word proposal:

> **Approach.** Render the PDF page to a PNG canvas. Operator opens it
> in MS Paint. Operator marks the roof perimeter in one color, drains
> in another, calibration line in a third. Script reads the canvas,
> filters by color, infers SW corner from bounding box, computes real
> dimensions. Output: a JSON file with bbox, area, drain positions, and
> a validation PNG that overlays detected features for visual sanity check.
>
> **Why this beats vector parsing.** Vector PDFs return ~9000 unrelated
> drawing primitives per page with no semantic labels. The hard problem
> isn't measurement; it's "which polyline is the actual roof outline."
> Human visual judgment resolves that in seconds — color marking lets
> us capture the human's judgment in a form the script can read.
>
> **Why MS Paint.** Zero-install. Already on every Windows machine.
> Operator already knows it.
>
> **Time estimate.** 3-4 hours for v1.0 covering one canvas, three colors
> (perimeter + drains + calibration). Validation on one real project
> before sign-off.

The operator approved the proposal in chat. The agent implemented.

### What v1.0 shipped

Four hours later, in a single tool directory created per `FOLDER_LAYOUT.md`:

```
Tools/RoofTakeoff/
├── .venv/
├── requirements.txt          # PyMuPDF, Pillow
├── MAINTENANCE_LOG.md         # decisions / errors / handoff
├── MARKUP_GUIDE.md            # one-page operator instructions
├── roof_takeoff_from_pdf.py   # the script
└── (output/ created on first run)
```

The first validation run measured the test project's largest roof
within **+1.05% of the operator's hand measurement**. Not perfect, but
sub-2%, which beat the operator's 5% tolerance comfortably.

### What the methodology had already done

Before any code was written:

- The directive forced a plain-language proposal — preventing the
  agent from going down a rabbit hole on PDF vector parsing.
- The folder layout gave the new tool a known home.
- The maintenance-log protocol was already enforced — the agent created
  `MAINTENANCE_LOG.md` in the new directory before the first commit
  of code.
- The naming convention applied to outputs (`<project>_<roof>_takeoff.json`).
- The session-end protocol forced a TASK_QUEUE entry, a memory note,
  and a maintenance-log handoff before sign-off.

This is what "compounding methodology" looks like in practice. None
of these acted as bottlenecks. Each one cost ~30 seconds and
prevented a downstream re-do.

## 2. The first memory entries

After Session 1, the agent and operator had two new memories worth
saving across sessions:

### `feedback_coordinate_convention.md` (feedback type)

```markdown
**Rule:** Roof coordinate origin is always the SW (lower-left) corner,
+X east, +Y north. Keeps all values positive.

**Why:** Every roof drawing has a different "natural" zero point. Fixing
the convention to SW means: (1) all derived values are positive, easier
to read; (2) downstream tools (tapered design, edge metal callouts)
share one frame of reference; (3) the agent doesn't have to ask each
session "what's your origin?"

**How to apply:** When measuring or computing derived positions on any
roof artifact, output values relative to SW corner. Don't introduce a
project-specific origin without explicit operator approval.
```

### `project_roof_takeoff_tool.md` (project type)

A short summary: tool exists, lives at `Tools/RoofTakeoff/`, current
version, dependencies, one-line how-to-run. Not a duplicate of the
maintenance log — just enough so the agent in the next session can
load this memory and know "the tool exists, here's the shape."

### What the methodology gained

The first memory was a **standing convention** the agent would
otherwise re-discuss every time. The second was a **lightweight
project pointer** that meant a future-session agent could load context
in seconds, not minutes.

Both followed the schema in `MEMORY_SCHEMA.md`: frontmatter + body
structured as **Rule → Why → How to apply**. Both got pointed at from
`MEMORY.md` index.

## 3. v1.1 → v1.5 — Color palette and protocol expansion

Over the next several sessions, the tool gained capabilities:

| Version | What was added | Why |
|---|---|---|
| v1.1 | Curb-detection color (orange) | Different operators need to count rooftop equipment; dropping that into the palette unblocks downstream tooling |
| v1.2 | Penetration-detection color (magenta) | Pipe / vent counting also feeds downstream cost |
| v1.3 | Per-project venv + pinned dependencies | Caught when a numpy version pin failed on a runtime upgrade |
| v1.4 | Scale flag (`--scale 1/4`) | Different drawings use different scales; hardcoding `1/16"=1'` was a silent bug on a project that used `1/4"=1'` |
| v1.5 | Calibration-line clustering for noisy drawings | A project with many CAD-rendered green elements broke calibration; switched from "all green pixels" to "longest connected green cluster" |

### The methodology under load

Every one of these versions was logged in `MAINTENANCE_LOG.md`.
Versions weren't tagged in any source-control sense; they're just
markers in the session-handoff sections of the log. But because the
log was *current* — updated during each session, not at the end of the
month — every version had a clear "what changed and why" record.

Several of the changes generated new memory entries:

- `feedback_pds_source_of_truth.md`: when measuring product weights,
  reach for the manufacturer's product-data sheet, not the agent's
  estimate. Triggered by an estimation that was off by ~15% from the
  PDS value.
- `domain_polyiso_rvalue.md`: a standing domain-knowledge note about
  how a particular material's R-value is calculated (long-term thermal
  resistance vs. nominal). Captured as `domain` type because it's
  long-lived domain knowledge, not project-specific.

### What broke that the methodology caught

The v1.4 scale issue was caught because an `INVENTORY.md` accuracy
spot-check (in the recurring-maintenance checklist) included a row
saying "this tool defaults to 1/16-scale drawings." The operator
read it during a routine cadence pass and asked, "what about my
projects at 1/4 scale?" The fix was a flag; took 15 minutes; the
catch was the inventory entry.

This is the methodology paying off in a non-obvious way. Without the
inventory, the operator would have run the tool on a 1/4-scale
project, gotten an area 16× too large, and *maybe* caught the error
or *maybe* not.

## 4. The variance protocol session

Two weeks in, the operator wanted to stop using the tool internally
and start *publishing measurements* — quoting external customers based
on tool output. That moment changed the methodology's load.

### The plain-language proposal

The operator's directive: "Before shipping this as a product, every
project gets the same number of re-runs so we have standardized
variance — when we win, why? when we're off, why?"

The agent wrote a one-page protocol proposal:

> **Standardized variance protocol.** For each new project to ship:
> N=3 markup runs by the operator (fresh markup each time, not copy-and-
> paste). Each run feeds the deterministic downstream pipeline. Output:
> a coefficient of variation (CV) per project plus a narrative
> explaining what drove the variance.
>
> **Why.** The pipeline downstream of markup is deterministic. All
> observed run-to-run variance comes from human marking judgment.
> Three runs lets us measure that variance.
>
> **Calibration vs. accuracy.** Calibration measurement (repeatability
> against the canvas itself) is sufficient for the *ship* claim;
> accuracy vs. external ground truth (where one exists) is an optional
> overlay. They are different claims. Don't conflate them.
>
> **Tracking.** A single `VARIANCE_TRACKER.md` per project area, with
> one row per `{project, roof, run}` triple.

The operator approved. Five projects went through the protocol. The
deliverable: a published variance number per project + a per-project
narrative.

### A small honest-disagreement moment

In an earlier draft of the protocol, the agent had conflated calibration
with ground truth. The operator pushed back: "Help me understand why
single calibration isn't enough." The agent re-thought it, agreed, and
the framework split into two distinct concepts.

That exchange got logged in the session's evolution log entry:
> **Lesson:** Operator pushback is information. The reframe was sharper
> than the original.

This is the directive's "be curious; ask; disagree openly" working in
both directions.

### What landed in the knowledge base

- A new doc in the operator's KM (knowledge management) directory:
  `Knowledge_Management/variance_protocol.md`. Status: `[DRAFT]`. Will
  promote to `[CONFIRMED-BY-OPERATOR]` after the 5-project validation
  pass.
- A new pointer in `MEMORY.md` to the protocol doc, so the agent
  loads it whenever variance-related work comes up.
- A new column in the recurring-maintenance checklist tracking the
  variance-protocol pipeline: which projects are done, which are in
  flight.

## 5. Failure modes the methodology caught

Three failures emerged during the 5-project pass. Each one was caught
by the methodology, not in spite of it.

### Failure 1 — Two adjacent roofs merged into one

On a project with two roofs sharing a height step, the script's
pixel-detection treated both as one polygon. Area was correct in
total, but downstream tooling needed *per-roof* numbers, and these
were now merged.

**Mitigation.** The operator and agent designed a new convention:
*dashed purple* line as a roof-joint bisector. Adobe (the PDF tool the
operator was already using) supports dashed strokes. The script reads
the dashed segments directly from the source PDF (vector source —
gaps in dashes don't matter), bakes them onto the perimeter mask
before flood-filling, and produces 2+ distinct roof polygons.

This was a v1.6 change. The change was logged in the maintenance log,
the markup guide was updated to a new step (5b), and the new convention
was reflected in the variance tracker.

### Failure 2 — Memory said one thing; current state said another

In the same session, the agent had a memory file that said the project's
total area was ~33,768 SF. The fresh script run produced 22,158 SF.
The vendor's reference number was 23,730 SF. Three numbers, two of
which clearly contradicted the third.

The agent flagged the disagreement instead of acting on memory. The
operator and agent investigated:

- Memory's 33,768 SF came from an early AI estimate before measurement
  was actually done.
- The vendor's 23,730 SF came from an authoritative third-party
  reference.
- The script's 22,158 SF was within ~6% of the vendor — consistent
  with a normal waste-factor band.

The conclusion: memory was wrong. The script was right. The vendor
agreed.

This led directly to the next two patterns.

### Failure 3 — A consultant's annotation broke the script

On one project, the consultant who had drawn the roof plan also drew
keynote-callout circles *over* the roof outline, fragmenting the
operator's purple perimeter into too many disconnected pieces. The
script's "bridge" parameter (which spans gaps in the perimeter mask)
exploded to 6.7 GB of memory before completing.

**Mitigation.** Killed the run. Added a hand-off note: "operator,
remark this page using a single continuous closed Polygon annotation
that traces an offset away from the consultant's keynote circles."
Documented in the per-tool maintenance log and the markup guide.

The methodology accepted "this isn't fixable in code" as a valid
conclusion. The fix is a markup discipline change, not a code change.

## 6. The single-source-of-truth declaration

The session that produced Failure 2 (memory ≠ current state) led to a
small but load-bearing change in the methodology itself.

### The problem

After the dust settled, the operator had area measurements scattered
across:

- `MEMORY.md` itself (in the project list).
- A per-project `PROJECT_SUMMARY.md` (in the project's vault folder).
- The `MAINTENANCE_LOG.md` of the tool that produced them.
- The `VARIANCE_TRACKER.md` for the variance protocol.

When any one of these got updated, the others were *supposed* to be
updated in lock-step. They weren't. Drift was inevitable.

### The declaration

```markdown
> **Per-domain measurements have one canonical doc; other docs link to it,
> not duplicate.**
>
> For roof takeoff measurements, `VARIANCE_TRACKER.md` is the single
> source of truth. `MAINTENANCE_LOG.md` records *novel tooling changes
> and notable failures only* — it does not record per-project
> SF / drain counts. `MEMORY.md` references the tracker by location,
> not by enumerated values. `PROJECT_SUMMARY.md` files reference the
> tracker, not their own measurement section.
```

### Why this is methodology, not just a tool decision

The pattern generalizes. Every domain in the operator's vault has
*some* kind of canonical measurement: pricing data, contact information,
project status. When the same data lives in three places, the third
place is always wrong.

The single-source-of-truth declaration became a *pattern* in the
operator's code-review wiki. The pattern can be applied to any
domain where data exists in multiple files: declare one doc canonical,
shrink the others to pointers.

This pattern was not part of the original methodology blueprint. It
emerged under load. The methodology's job was to *capture it* —
which it did, both in the wiki and as a feedback memory entry.

## 7. The validate-then-update standing rule

The same session produced one more standing rule, also previously
absent from the methodology.

### The problem

When `MEMORY.md` and `PROJECT_SUMMARY.md` disagreed with the vendor's
numbers, the temptation was to update everything to match the script
output. The agent caught itself about to do exactly that — and stopped.

What if the script was wrong and the older docs were right? How do
you know which to trust?

### The rule

```markdown
> **When docs disagree with newer better-validated data, update toward
> better validation AND retest the validation path before signing off.**
>
> **Why:** Stale information beats new wrong information. Update direction
> matters less than confirming the new data is *actually* validated.
> "The script said so" is not validation; "the script said so AND we
> ran it twice AND it agrees with the vendor's reference" is.
>
> **How to apply:**
> - Identify the disagreement.
> - Identify the *most validated* current data point.
> - Update conflicting docs toward that point.
> - **Re-run the validation path** (not just the failing measurement —
>   the whole validation chain).
> - Sign off only after the re-run agrees.
```

### Where it landed

Saved as a feedback memory: `feedback_validate_then_update.md`. Pointer
added to `MEMORY.md`. Cross-referenced from `KNOWN_LIMITATIONS.md`
(memory misses) as a mitigation: when memory and current state
disagree, this rule is the protocol.

### Why this matters

The variance protocol session produced *two* new methodology patterns:
single-source-of-truth and validate-then-update. Neither existed
before. The methodology's claim is not "we anticipated everything"
— it's "the rhythm of session protocols + memory + maintenance logs
+ explicit failure capture means new patterns get *recorded* and
*reused* instead of getting forgotten."

Two patterns from one session. That's the compounding.

By the end of the 2-week arc, the memory store had grown from ~30

The dashed-purple bisector convention exists *because* the agent
cannot reliably interpret a generated drawing the way a human can.
The operator looked at a problematic project, saw "two adjacent
roofs sharing a height step," and named the structural relationship.
The agent could not have proposed that on its own.

This is `KNOWN_LIMITATIONS.md`'s "can the agent see what the operator
sees?" The case study confirms the limit. The mitigation is the
same as in the limitations doc: the operator stays in the loop on
visual interpretation; the tool implements what the operator names.

## 9. What an operator copying this case would change for their domain

For anyone considering applying this methodology to their own work,
here are the load-bearing elements vs. the domain-specific elements
in this case:

### Load-bearing (keep)

- **Plain-language proposal before code.** The agent should never
  start coding without operator approval of the approach. This single
  rule shaped the tool's whole architecture.
- **One canonical doc per domain.** Whatever your domain's canonical
  data is — measurements, customers, transactions, anything — declare
  one doc as the source of truth.
- **Calibration vs. accuracy as distinct concepts.** Wherever you
  have repeatability questions and ground-truth questions, keep them
  separate. They answer different questions for different audiences.
- **Failure capture as standing protocol.** Every failure that takes
  more than 15 minutes to diagnose gets a maintenance-log entry.
  Every standing rule that emerges from a failure gets a feedback
  memory.
- **Honest accounting in published artifacts.** The variance protocol
  + the validate-then-update rule + this case study itself are
  published *with* their limitations.

### Domain-specific (substitute)

- **Pixel detection on a colored canvas.** This is a spatial-measurement
  trick. Your domain may use entirely different inputs.
- **The five-color palette.** Specific to physical-structure drawings.
- **The variance protocol's N=3 runs.** A choice that fits this
  particular tool's marking-variance load. Other tools may need N=5
  or N=1.
- **Vendor reference numbers as ground truth.** Domain-specific. Your
  ground truth comes from somewhere else.

### Things that will surprise you

- **The methodology produces patterns it didn't start with.** Single-
  source-of-truth and validate-then-update were *not* in the v1.0
  methodology. They emerged. Plan for that.
- **The recurring-maintenance checklist catches more than you expect.**
  The 1/4-scale bug in v1.4 was caught because the inventory had a
  row saying "defaults to 1/16-scale drawings." A spot-check noticed
  the implication.
- **You will under-curate memory.** Every operator does. Build the
  cadence into your week or accept the cost (per `KNOWN_LIMITATIONS.md`).
- **The agent will sometimes be wrong with confidence.** The
  validate-then-update rule exists because of one of those moments.
  Trust your protocols, not the agent's tone.
