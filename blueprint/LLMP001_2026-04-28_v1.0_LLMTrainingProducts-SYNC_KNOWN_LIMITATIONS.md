## Why publish this at all

Three reasons.

1. **You will hit these failure modes.** If we hide them, you'll think
   you're doing something wrong. You're not. The system itself has
   limits, and naming them lets you work around them instead of
   blaming yourself.
2. **The mitigations are part of the methodology.** Every limit below
   has a workaround. The workarounds are real work — captured in
   protocols, scripts, audit gates. Adopting the methodology means
   adopting the workarounds, not just the happy-path patterns.
3. **AI tooling is iterating fast.** What's broken in 2026 may be solved
   by 2027. This doc dates each limit and notes what we're watching for
   as a fix.

This is not a "honesty branding" exercise. This is the punch list.

## The three big ones

### 1. Memory misses

**What it looks like.**

The agent doesn't recall something it *should* recall. You wrote a
feedback memory three weeks ago saying "never use mocks in integration
tests." Today the agent writes integration tests with mocks. You
correct it. It says, "you're right, I should have remembered." But it
didn't.

Or: you saved a project memory about why a particular module exists.
Today the agent suggests removing the module. The reason was in memory.
The agent didn't load that file.

**Why it happens.**

Memory is filesystem-based topic files plus an index. The agent decides
what to load by scanning the index descriptions. If the description
doesn't match the current task's vocabulary, the topic file stays
unloaded — even when it's directly relevant. The mechanism is
keyword-matching against descriptions, not semantic understanding of
the index entry against the conversation.

The longer your memory store grows, the more this fails. With 5 topic
files, the agent loads anything that *might* be relevant. With 50
topic files, it has to pick — and its picks are imperfect.

**Ramifications.**

- You correct the same thing twice, three times, more.
- You lose trust in memory. Stop saving things. The system decays.
- Decisions you thought were settled get re-litigated.

**How we're iterating.**

- **Better descriptions.** The single biggest lever. A vague
  description ("background tasks") rarely matches; a specific one
  ("never sign off with background tasks running — they orphan and
  don't surface errors") matches reliably. Curation work below.
- **Cross-references in directives.** Critical feedback memories get
  short-pointed in `DIRECTIVE.md` so they're auto-loaded with the
  contract, not gated behind index lookup.
- **Watching:** semantic-search retrieval (RAG-style) for topic files
  via embeddings. Cheaper-than-a-full-context-window, more reliable
  than keyword matching against descriptions. Not adopted yet — adds
  a vector store to the stack and the cost/complexity tradeoff isn't
  obviously worth it for a single-operator vault. May change with
  vault scale.

### 2. Curation effort

**What it looks like.**

You committed to memory hygiene. You write feedback memories whenever
something gets corrected. After a month, you have 30 topic files.
Some are stale. Some duplicate each other. The index is at 180 lines
and growing. Reading it eats real screen time. You start skipping
the curation step at session end.

A month later, the index is at 240 lines and the auto-load truncates.
The bottom 40 entries don't load anymore. Memories silently disappear
from the agent's context.

**Why it happens.**

Memory is write-cheap, curate-expensive. Saving a memory takes 30
seconds. Reading every topic file, deciding what's stale, merging
duplicates, rewriting vague descriptions — that's an hour, easy.
And that hour produces no visible output.

The system doesn't enforce curation. There's no test suite that fails
when memory rots. The agent doesn't surface "by the way, you have
three memories that say nearly the same thing." So curation slips.

**Ramifications.**

- Index bloats past truncation. Memories silently stop loading.
- Stale memories produce wrong recommendations. Worse than no memory.
- Duplicate memories conflict. Agent picks one — sometimes the
  outdated one.
- You stop trusting the system. Stop using it. Pattern decays.

**How we're iterating.**

- **Recurring maintenance cadence.** A `SESSION_ENV.md` checklist
  surfaces "review memory index" as a periodic task with a last-run
  date. When the cadence stretches, it's visible.
- **Two-part discipline (in `MEMORY_SCHEMA.md`).** Create as many sub-files
  as needed; *also* improve memory processes when context is lost.
  Both halves matter.
- **Honest acknowledgment in this doc.** If you can't sustain
  curation, the methodology is fragile. Plan for it explicitly.
- **Watching:** scripts that surface duplicate-detection (similarity
  scoring across memory files), index line-count alerts, age-based
  staleness flags. Tooling that reduces curation cost so curation
  actually happens.

### 3. Context drops

**What it looks like.**

You're 90 minutes into a session. You've made 15 file edits. The agent
has been right on track. You ask it to "apply the same pattern to the
next file." It does — but the pattern it applies is from 30 minutes
ago, not from the most recent change. It missed the refinement you
made between minute 60 and minute 90.

Or: you switch from one project to another mid-session. The agent
keeps using vocabulary from the prior project. Subtle drift, but
present.

Or: a long output gets summarized internally, and the summary loses
the specific detail you needed.

**Why it happens.**

Context windows are large but not infinite, and they're not
*reliably* coherent. (Context windows are measured in **tokens** — the
unit the model bills against, roughly 0.75 words per token. Modern
windows are 200,000 tokens and growing.) Information at position
50,000 tokens of a 200,000-token window is loaded — but the agent's
attention to it depends on phrasing, recency, and how much intervening
content has accumulated.

For long sessions, the agent itself (or the harness) may run a
compaction step that summarizes earlier conversation to make room.
Compaction loses detail. The agent thinks it has the whole
conversation; what it has is a lossy compression.

**Ramifications.**

- Late-session work drifts from early-session decisions.
- Multi-step refactors come out inconsistent across files.
- You catch the inconsistency in review and have to re-explain.
- Trust degrades over a long session even when the early hours were
  excellent.

**How we're iterating.**

- **Three gates** (saved as feedback rule, see
  `feedback_context_drop_audit.md` in our reference vault):
  before answering questions about prior work, before saving a
  memory based on inferred state, and on cold-read of a doc — the
  agent verifies against current state rather than recalling.
- **Plain-language proposals before code** (DIRECTIVE.md §8). Forces
  the agent to restate its understanding before committing. Catches
  drift early.
- **Session protocols.** Start-of-session re-reads `MEMORY.md`. End-of-session
  writes a summary. Prevents *between-session* drift; doesn't fully
  solve *within-session* drift.
- **Stop-and-curate during the session.** **The primary discipline.**
  Whenever you notice drift — the agent applying an old version of a
  pattern, slipping into the wrong project's vocabulary, or losing a
  detail you set earlier — pause. Re-read the relevant memory or doc.
  Restate the constraint to the agent. Resume. This works for most
  drift, far more often than ending the session and starting over. The
  point is to use it absolutely whenever you notice the need; the
  failure mode isn't the discipline missing, it's not noticing in time.
- **Shorter sessions only when stop-and-curate isn't enough.** A real
  but rarer case: even after you stop, re-read, and restate, the agent's
  interpretation of the freshly-re-read material is still being colored
  by the long-context overhang. The agent appears to acknowledge the
  reset but its outputs continue drifting in the same direction. When
  you're seeing that — and you've already tried stop-and-curate twice —
  ending the session and starting fresh is cheap insurance for high-
  stakes work. Not the first move; the escalation when the first move
  isn't holding.
- **Watching:** native memory-management features in agent harnesses,
  longer-stable context windows, better internal compaction strategies.
  Some of this is being addressed by frontier models. Watch the
  releases.

## Smaller open problems

### Source-cite correctness vs. fluency

The system can say correct things and incorrect things in the same
paragraph, with the same level of confidence. Source citation
(footnoting every claim back to a primary document) is the workaround.
The discipline of "if you can't cite it, don't say it" is operator-
enforced; the model itself doesn't know when it's making things up.

**Track record doesn't help here.** The model can be confidently wrong
on the same task it has been reliably right on multiple times before.
Past correctness is not a predictor of next-turn correctness — every
output gets the same source-cite scrutiny regardless of how many
clean runs preceded it. Reliability earned in turn 1 does not transfer
to turn 47.

### Multi-system integration

Combining open-source + frontier, or multiple frontier models, is
where consistent, repeatable workflows fall apart. Different models
have different defaults, different safety policies, different
context-window tricks. Coordinating them is real work and it doesn't
generalize across stacks. We name this as an open problem rather than
pretending we have a clean answer.

### Can the agent see what the operator sees?

For visual-precision work — drawings, takeoffs, layouts, diagrams —
there is no current way to confirm that the agent's interpretation of
a generated artifact matches the artifact's actual data. The model can
*describe* an output. It cannot reliably verify that the description
matches the ground truth. Until that gap closes, the operator is the
only ground truth for verification.

### Cost portability

Frontier models are getting more expensive faster than cheaper. If
your workflow is bound to one provider's specific features, you're a
price-taker. The methodology's defense is **plain text on a
filesystem**: markdown documents that any model can read. Switching
providers becomes a decision, not a migration. But the principle has
a cost — you forgo provider-specific features that might genuinely
help.

### Verification gap

Generated code can pass tests and still be subtly wrong. Generated
documentation can be internally consistent and externally false.
Generated diagrams can look right and have wrong data. Verification
is the operator's job, supported by audit gates and review protocols
— but the *tooling* for verifying AI output is far less mature than
the tooling for generating it.

## What this means in practice

For the operator considering this methodology:

1. **Plan curation time, not just creation time.** The system needs
   weekly or biweekly maintenance. Build it into your cadence or it
   doesn't happen.
2. **Verify before relying on memory recall.** When the agent says
   "we decided X," check the current state of the relevant code or
   doc. Don't act on memory alone for high-stakes decisions.
3. **Keep critical rules in the auto-loaded directive.** Anything that
   matters every session shouldn't be gated behind index lookup.
4. **End long sessions and start new ones for high-stakes work.**
   Coherence degrades over very long sessions. Reset is cheap.
5. **You will feel the work.** This is not magical efficiency. The
   compounding payoff is real, but so is the daily discipline.

## What's NOT a known limitation

Not every grievance with AI tooling belongs here. These are *tooling*
limits. They are not:

- Excuses for sycophancy or shallow output. The agent should push back,
  ask, and disagree. If it doesn't, that's a directive problem, not a
  limit.
- Reasons to accept hallucinations. Source-cite or don't say it.
- Reasons to skip review. The operator is ground truth.
- Reasons not to start. The methodology delivers value with these limits
  in place. They just need to be named.
