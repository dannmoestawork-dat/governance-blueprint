# LESSONS_SINCE_V1 — eight rules the methodology learned after v1.1
## Classification: Tier 0 (public methodology)
## [AI-ASSISTED] — 2026-11-10 — v1.2 addition (module #20) — Apache 2.0

> **Why this document exists.** v1.0 and v1.1 were written in the first five months of
> running this methodology every day. The months since produced rules that the earlier docs
> do not contain. Following this product's own editorial process, nothing in v1.0 or v1.1 was
> rewritten: the new rules live here, each with the failure that earned it. None of them
> contradicts an earlier doc; each one closes a gap that an earlier doc left open.

## 1. Cap the memory index in bytes as well as lines, and enforce the cap with a script

`MEMORY_SCHEMA.md` says to keep `MEMORY.md` under 200 lines. That is necessary but not
enough: harnesses also stop reading at a **byte** limit, and an index of 150 long lines can
pass the line rule while its tail is silently cut off. The agent never sees the cut, so it
never reports it.

- Measure your harness's real read limit once. Set your cap below it, as an exact number of
  bytes.
- Enforce the cap with a small script that runs automatically (for example, a hook at session
  start) and prints the measured size. A rule that lives only in prose gets broken under
  load, by the same agent that wrote it.

## 2. Rotate, never trim

When the index is full, the tempting move is to shorten entries until it fits. Each trim
loses a little context, and nobody can see what was lost.

- **Before removing anything, copy the index verbatim to a dated archive file.** No copy, no
  removal.
- Move whole blocks to topic files, leave a one-line pointer naming where they went, and
  confirm the moved text reads back identically (compare a hash).
- **Rotate before you add**, not after the cap is already blown.

## 3. Never trust a green

A check that has never been seen to fail is not yet a check.

- When you build a gate (a test, a scan, a validator), **make it fail on purpose once** and
  watch it refuse. Only then record it as working.
- Some tools exit with success even when they fail. Gate on the tool's own summary line
  (for example `passed=12 failed=0`), not only on its exit code.
- **A script that prints "OK" is not an artifact that works.** If the output is a drawing, a
  page or a document, open it and look at it before you call it done.

## 4. Search before you build

The agent's habit is to build new machinery. Every new part is new surface for failure, and
the failures tend to move into the additions.

- Before writing a tool, search for the one that already exists (your own vault, installed
  libraries, the services already running), and **write down what you searched for and what
  you found.**
- When something has completed successfully three times, the fourth run uses the third
  run's exact command, changing **one** thing.
- A safeguard earns its place by protecting something that has already worked. Do not guard
  a path that has never run in its simple form.

## 5. Runbooks rotate too

A runbook (module #19) that is never trimmed eventually becomes too long to read in one
pass, which defeats its purpose as a cold-start handoff.

- Set a size gate (we use 1,500 lines or 60 KB).
- Over the gate, move **finished** stages verbatim to a dated history file beside the
  runbook, leaving one dated pointer line that names the file and what is in it.
- **Never move** the status bar, open questions, the Code Files list, the Wiki Aspect, or any
  stage that has not run yet. Identify each moved block by an ID and a hash, never by line
  number, so it can be restored exactly.
- Keep Run History entries to one line each. Lessons go to memory or to the knowledge base.

## 6. The version bump and the version entry are one act

Any product another session, machine or person relies on carries a version. **Whenever its
format, its information or its process changes, the version goes up and an entry is written
at the same moment**, saying four things: the new version and date, what changed (the
mechanism, not "improvements"), why (the trigger), and who signed it. Then search for every
place that cites the old version and update it. A stale citation is a false claim.

## 7. Every plan carries an "Out of scope" section, and it is never empty

Write it while the plan is being questioned, before any build step exists. An empty one means
nobody found the edge of the work yet. Something ruled out of scope does not quietly come
back: it returns only as a new item with a new reason, so the reversal is visible.

## 8. Every controlled vocabulary has one machine-readable home

When a word becomes a field name, a status value or a tag (anything a program reads), it
goes into one registry file with a plain-language definition, the single question it answers
(one field, one axis: never mix identity, action, priority and workflow state in one value
set) and its ordering. Look for a published standard before coining a term. The test: could
another tool read your files correctly without reading your notes?
