# NAMING_CONVENTIONS.md — Bracket-Token Filename Pattern
## Classification: Tier 4 (internal — operator + agent)
## [AI-GENERATED] — 2026-04-28 — Apache 2.0
## Part of: LLM Training Products v1.0

> **Purpose.** Define a single, universal filename pattern that makes the
> filesystem itself navigable and turns every filename into a small piece of
> metadata. Includes the **`LOCAL` / `SYNC` / `SHARE`** sync-state tag — the
> privacy/security signal at the heart of sovereign-workstation hygiene.

---

## The format

**Notation:** `[Project][DATE][VERSION][Folder-SyncTag][Etc].ext`

**Filename:** Five fixed-position fields separated by `_`. Within a field,
words are separated by `-`. **No literal brackets.**

**Worked example:**

```
RTK014_2026-04-28_v1.6_RoofTakeoff-SYNC_Variance-Tracker.md
```

Parsed:

| Field | Value | Meaning |
|---|---|---|
| Project | `RTK014` | Roof Takeoff project, 14th initiative |
| Date | `2026-04-28` | Created (or last semantically updated) on 2026-04-28 |
| Version | `v1.6` | Sixth minor release of v1 |
| Folder-SyncTag | `RoofTakeoff-SYNC` | Lives in `RoofTakeoff/`, replicated to cloud (`SYNC`) |
| Etc | `Variance-Tracker` | This is the variance tracker file |

## Field-by-field

### 1. Project — alphanumeric mnemonic

**Format:** 3–6 letters + 3-digit sequential ID. Letters allude to the project
so the filename signals what it points to.

**Examples:**
- `RTK014` — Roof Takeoff project 14
- `LLMP001` — LLM Training Products project 1
- `OBT003` — Owner Budget Tool project 3
- `CRM042` — CRM project 42

**Rules:**
- Letters: 3–6 chars, all caps preferred for visibility (`RTK` not `rtk`).
- Numbers: 3 digits, zero-padded (`014` not `14`). Pad-3 keeps lexical
  sort working through `001`–`999`.
- Project mnemonic is **stable** across the project's life. Versions and
  dates change; the project ID does not.

**Why alphanumeric (not opaque IDs).** A filename starting with `RTK014`
tells you, at a glance, that you're looking at the Roof Takeoff project.
A filename starting with `P-2024-1138` tells you nothing without looking
something up. The mnemonic *is* the navigation.

### 2. Date — ISO-8601

**Format:** `YYYY-MM-DD`

**Why ISO-8601:** Sorts correctly when alphabetical-sorted (which is what
filesystems do). `2026-04-28` < `2026-05-01` < `2026-12-15` — the
filesystem itself becomes a chronological index.

**Which date:** Creation date is fine for most files. For files that get
updated, use **last semantic update** (i.e., a new date when the content
materially changes). Don't update the date for whitespace fixes or typos.

### 3. Version — semver-lite

**Format:** `vN.N` (or `vN.N.N` if you need patch granularity)

**Examples:** `v1.0`, `v1.6`, `v2.0`, `v1.6.3`

**When to bump:**
- **Major (`v1.0` → `v2.0`):** Breaking change. Old version is
  incompatible with new.
- **Minor (`v1.0` → `v1.1`):** Backwards-compatible change. Adds
  capability without breaking old usage.
- **Patch (`v1.6` → `v1.6.1`):** Bug fix. No new capability, no
  behavior change for correctly-running cases.

**For documents (not code):** Use `vN.N`. Major bump for structural
revision; minor for content additions. Don't bother with patch-level on
prose.

### 4. Folder-SyncTag — folder mnemonic + privacy/security signal

**Format:** `<Folder-Mnemonic>-<SyncTag>`

**Folder mnemonic:** A short version of the folder name where the file
lives. Use hyphens for multi-word: `RoofTakeoff`, `LLMTrainingProducts`,
`CRM-Companies`.

**Sync tag — three states (binding):**

| Tag | Meaning | Where it lives |
|---|---|---|
| `LOCAL` | Airgapped — never leaves this machine | Sovereign workstation only; not in cloud sync |
| `SYNC` | Cloud-replicated — backed up but not externally distributed | OneDrive / iCloud / Dropbox / Git |
| `SHARE` | Externally distributed — sent to clients, partners, or published | Out the door |

**Why the sync tag is load-bearing.** It is the single grep-able privacy
signal in your vault. `find . -name "*_LOCAL_*"` finds everything that
must never leave this machine. `find . -name "*_SHARE_*"` finds everything
that *has* left and is therefore in third-party hands. This is structural
privacy hygiene — not policy, not memory, not someone-remembering — but
visible in the filename itself.

**Default:** Today, before air-gapped infrastructure exists, almost
everything is `SYNC` (cloud-replicated). When you build local-only
infrastructure (sovereign workstation, air-gapped device, etc.), `LOCAL`
becomes meaningful. `SHARE` applies the moment a file is sent externally.

**Promotion rule:** A file's sync tag can only become *more permissive*
(`LOCAL` → `SYNC` → `SHARE`) with explicit operator approval. This
mirrors the Tier classification downgrade gate (see `GOVERNANCE.md` §6a).

### 5. Etc — free-form discriminator

**Format:** Any descriptor. Hyphens for multi-word. Avoid underscores
(reserved for field separator).

**Examples:**
- `Variance-Tracker`
- `Roof27A-Takeoff`
- `Q3-Pricing-Update`
- `DIRECTIVE` (single-word OK)

**Use cases:**
- File role (`DIRECTIVE`, `GOVERNANCE`, `MEMORY-SCHEMA`)
- Sub-element (`Roof27A-Takeoff`, `Phase-2-Build`)
- Deliverable type (`Quote-Bunk`, `Email-Draft`, `Slide-Deck`)

## Special-case files (canonical names retained)

The following files keep their **canonical names** because they're tooling-level
conventions that other software (GitHub, npm, OS file managers, IDEs) special-cases:

| File | Why retained |
|---|---|
| `README.md` | GitHub auto-renders. Most tools special-case it. |
| `LICENSE` (or `LICENSE.md`, `LICENSE.txt`) | GitHub legal panel detects only canonical names. |
| `.gitignore`, `.dockerignore`, `.env.example` | Tool conventions. |
| `requirements.txt`, `package.json`, `Cargo.toml`, etc. | Build-tool conventions. |
| `CHANGELOG.md`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md` | Open-source convention. |

**Everything else** in your vault should follow the bracket-token convention.

---

## Folders vs. files

The convention applies primarily to **files**. Folders use a simpler pattern:

- Use **underscores or hyphens** for word separation (pick one and stick with it).
- For project subfolders, prefix with the **project mnemonic**: `RTK014_Example_Project/`,
  `LLMP001_TrainingProducts/`.
- **Sync state on folders** inherits from the most-restrictive child file. A
  folder containing any `LOCAL` file must itself be in a `LOCAL`-eligible location.

## Worked rename examples

If your existing vault doesn't follow the convention, here's how to migrate
common file types:

| Old name | New name |
|---|---|
| `notes.md` | `RTK014_2026-04-28_v1.0_RoofTakeoff-SYNC_Notes.md` |
| `meeting_2026-04-28.md` | `OPS001_2026-04-28_v1.0_Operations-SYNC_Meeting-Notes.md` |
| `Q3 budget v2.xlsx` | `BGT003_2026-04-28_v2.0_Finance-LOCAL_Q3-Budget.xlsx` |
| `final_proposal.docx` | `RTK014_2026-04-28_v3.0_RoofTakeoff-SHARE_Proposal.docx` |
| `client_email_draft.txt` | `RTK014_2026-04-28_v1.0_RoofTakeoff-SYNC_Email-Draft.txt` |

Note the last two: the proposal is **SHARE** (already sent or about to be);
the email draft is **SYNC** (still internal). Both reference the same
project (`RTK014`).

## Parsing the convention programmatically

Because field positions are fixed and separators are non-overlapping (`_`
between fields, `-` within fields), filenames are trivially parseable:

```python
from pathlib import Path

def parse_filename(filename: str) -> dict | None:
    """Parse a bracket-token filename into its 5 fields.

    Returns None for non-conforming filenames (e.g., README.md).
    """
    stem = Path(filename).stem  # drop extension
    parts = stem.split("_")
    if len(parts) != 5:
        return None  # not in convention (e.g., README, LICENSE)

    project, date, version, folder_sync, etc = parts

    # Folder-SyncTag splits on the LAST hyphen so multi-word folder
    # names work: "Roof-Takeoff-SYNC" → ("Roof-Takeoff", "SYNC")
    if "-" not in folder_sync:
        return None  # malformed
    folder, sync_tag = folder_sync.rsplit("-", 1)

    if sync_tag not in ("LOCAL", "SYNC", "SHARE"):
        return None  # invalid sync state

    return {
        "project": project,
        "date": date,
        "version": version,
        "folder": folder,
        "sync_tag": sync_tag,
        "etc": etc,
    }
```

This means filename-driven scripts are easy: "find all SHARE-tagged files
older than 90 days" is one `find` + one parse. "Group all files by project
ID" is two lines. The filename is structured data.

## Why this convention vs. alternatives

**Alternatives considered:**

| Approach | Why not |
|---|---|
| Date-only prefix (`2026-04-28_notes.md`) | No project context; project history scatters across the date axis |
| Project-only prefix (`RTK014_notes.md`) | No version, no date, no privacy signal |
| YAML frontmatter inside the file | Invisible until you open the file; not greppable from `ls` |
| Directory-based (`RTK014/2026-04-28/v1.0/notes.md`) | Hides the metadata in the path; hard to grep across projects |
| UUIDs (`f47ac10b-58cc-...md`) | Opaque; meaningless to humans |

**Why this one wins:** All metadata is visible at `ls` time. All metadata
is greppable. The format is fixed-position so parsing is trivial. The
filename itself becomes a small index entry without needing a database.

**Cost:** Filenames are longer. ~50 characters typical. That's a real
cost (annoying to type) but small (filesystems handle 255+ chars; modern
shells autocomplete; the verbosity is *the feature*, not a bug).

## Adoption tips

1. **Start fresh, don't backfill.** Apply the convention to all new files.
   Migrate existing files only when you touch them anyway.
2. **Use shell aliases / snippets** to generate the prefix. A small script
   that takes (`project`, `etc`) and outputs the full filename saves typing.
3. **Tab completion is your friend.** Most shells autocomplete after the
   project prefix, so you only type the unique part.
4. **The agent can do the renaming.** Once the convention is in
   `DIRECTIVE.md`, an LLM agent can rename files conformantly when asked.
5. **The convention is yours to bend.** "Use Case Conventions are for the
   user." If your domain needs a 4th field, add it. Just stay
   consistent within your vault, document the deviation in this file,
   and don't break the parser.

## Maintenance

When to update this file:
- You add a new sync state (rare — `LOCAL`/`SYNC`/`SHARE` should cover most needs)
- You add a project mnemonic family that warrants documentation
- You decide to deviate from the convention for a class of files

When NOT to update:
- New project IDs being assigned (those go in `INVENTORY.md` or `TASK_QUEUE.md`)
- Routine renames of individual files
