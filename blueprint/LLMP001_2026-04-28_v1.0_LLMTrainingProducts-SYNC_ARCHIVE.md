> **Purpose.** When content is deleted from anywhere in the vault, a

> Saves future-you from "did I delete that on purpose, or was that a

---

## Why an archive exists

Three reasons.

1. **Reversibility.** Cloud-sync version history catches most accidents,
   but version history vanishes after the provider's retention window.
   The archive's text record outlives that window.
2. **Provenance trail.** When someone (operator, agent, future
   collaborator) finds a reference to a file that no longer exists, the
   archive answers "where did it go?" without re-litigation.
3. **Governance.** Some deletions need explicit operator approval
   (Tier 4–5 content). The archive records the approval alongside the
   action.

---

## When to write to ARCHIVE

Two distinct cases.

### Case 1 — Deletion for debugging or error correction

**No archive entry needed.** If you're deleting a stub, an empty
file, a typo'd filename, or a never-used scratch file — just delete.
The archive isn't a diary of every keystroke.

### Case 2 — Deletion for reorganization, supersession, or removal of meaningful content

**Archive entry required.** Examples:

- A document is being replaced by a more canonical version.
- A directory is being collapsed into a parent.
- A tool is being deprecated.
- Content is being moved out of one classification into another
  (e.g., demoting Tier 4 prose to a public-Tier 0 doc — record
  the rewrite).
- Multiple files are being consolidated into one.

When in doubt: archive. The cost of an extra archive entry is low.
The cost of a deletion you can't reconstruct is real.

## What goes in vs. what doesn't

**In the archive:**
- Reorganization deletions.
- Tool deprecations.
- Document supersession.
- Directory collapses.
- Bulk cleanups (deleted prototype N exploration files at once).

**Not in the archive:**
- Routine debug edits (typos, empty files, stubs).
- Renames (those go in the tool's `MAINTENANCE_LOG.md`).
- File moves *within* a tool's directory (per-tool log).
- Auto-generated artifacts that get rebuilt (caches, generated PDFs,
  rendered images).
- Sensitive content that can't be safely logged. (For Tier 5 content
  deletion, log the *fact* of deletion without restating the
  content.)

## Cross-reference protocol

When the operator (or agent) is editing a doc that previously
contained text now in the archive — the new doc should say:

> *Earlier draft of [section]: see ARCHIVE.md, YYYY-MM-DD entry.*

This stops "where did the discussion of X go?" loops. The archive is
linkable; use the link.

---

## Maintenance

- **At deletion time:** write the entry. Don't batch end-of-session;
  archive as you go.
- **Quarterly:** re-read the archive for the previous quarter. Are
  there patterns? Frequent reorganizations of the same area suggest a
  layout problem.
- **Annually:** consider partitioning by year (`ARCHIVE_2025.md`,
  `ARCHIVE_2026.md`) if the file gets unwieldy. Keep the index
  accessible at `ARCHIVE.md` pointing to the year files.

---

## What this file replaces

Without it, deletions live only in:

- Cloud-sync version history (which times out).
- Git history (which is hard to grep semantically).
- Operator memory (which is unreliable).

The archive is a third source — durable, greppable, and contextual.
It's cheap insurance.
