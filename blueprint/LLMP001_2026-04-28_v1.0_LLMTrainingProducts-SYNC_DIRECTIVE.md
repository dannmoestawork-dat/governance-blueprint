## Part of: LLM Training Products v1.0

> **Purpose of this document.** This is the file your LLM/agent reads FIRST
> at every session start. It establishes the contract between you (the
> operator) and the agent: who you are, what you're working on, the
> guardrails, and the standing rules. Everything else in your vault
> defers to this file.

> **How to use this template.** Copy `templates/DIRECTIVE.md` to your
> vault root, rename it to whatever your harness expects (e.g.,
> `CLAUDE.md` for Claude Code, `AGENT.md` for some others), and fill
> in the placeholders. Read this commentary version once to understand
> *why* each section exists.

## Section 1 — Operator Identity

```markdown
## 1. Operator Identity
- **Operator:** [your name]
- **Role:** [what you do — e.g., "independent legal researcher" or
  "lab notebook keeper" or "freelance technical writer"]
- **Domain:** [your field — e.g., "patent litigation," "marine biology,"
  "commercial real estate underwriting"]
- **Core objective:** [one sentence on what you're trying to accomplish
  with the agent — e.g., "synthesize case law into actionable client
  memos," or "maintain a structured experiment log across multi-month studies"]
- **Philosophy:** [one sentence on your working principle — e.g., "evidence
  over speculation," "compounding notes over one-shot answers"]
```

**Why this section.** The agent's tone, depth, and vocabulary should match
yours. An LLM with no operator profile produces generic output; an LLM that
knows you're a working scientist outputs scientific prose, not marketing
copy. The first sentence the agent ever reads should anchor it to your
context.

**What stays generic vs. what gets specific.** Domain-specific. The agent
should *know* your field. Don't say "knowledge worker" — say what you
actually do.

## Section 2 — Repository Layout

```markdown
## 2. Repository Layout
- Project-specific context lives in each project's directory
  (see each project's `MAINTENANCE_LOG.md` and `PROJECT_CONTEXT.md`).
- Reference data (read-only inputs) is indexed in `DATA_SOURCES.md`.
- Agent-spawned work should reference project docs, not this file.
```

**Why this section.** Tells the agent where to find context for *specific*
work without bloating this directive. This file is the *contract*; per-project
docs are the *details*. Auto-loaded files cost tokens at every turn — keep
them small.

## Section 3 — Provenance & Attribution

```markdown
## 3. Provenance & Attribution
Tag all generated content for trust and credit tracking:
- **[AI-GENERATED]** — File or draft created entirely by an LLM.
- **[AI-ASSISTED]** — Human edited the AI's initial output.
- **[VERIFIED]** — Operator has technically reviewed for accuracy.
```

**Why this section.** Three tags. Every artifact gets one. This is how you
build a trust trail: at any moment you can grep for `[VERIFIED]` and know
exactly what's been reviewed. Without provenance tagging, AI-generated
content becomes indistinguishable from your own work — and that's a
correctness *and* attribution problem.

## Section 4 — Operational Guardrails

```markdown
## 4. Operational Guardrails
- **Data Privacy:** Redact personal identifiers before any external output.
- **Source of Truth:** Marketing/external claims must cross-reference
  primary sources. [Substantive truth] over [surface polish]. Always.
- **Scope:** Read and write within `[your_vault_root]/` and its subdirectories
  only. Do not access parent directories or unrelated personal files.
```

**Why this section.** The agent's *blast radius*. If something goes wrong,
how bad is it? Restricting scope to your vault root means a runaway loop
can't touch your tax docs or your personal photos. The "source of truth"
clause prevents the agent from confidently stating things that aren't grounded
in your reference data.

## Section 6 — Maintenance Log Protocol

```markdown
## 6. Maintenance Log Protocol
Every directory with scripts must include a `MAINTENANCE_LOG.md` with:
1. **Error Log** — Date-stamped errors, root causes, resolutions.
2. **Script & Approach Reasoning** — Why each script exists, alternatives
   considered.
3. **Dependencies** — Libraries, versions, install locations.
4. **Session Handoff Notes** — End-of-session summary and next steps.

Rules: Create when first script is written. Update during development,
not just at the end. Tag entries per Section 3. Keep entries concise.
```

**Why this section.** The MAINTENANCE_LOG is *per-tool* memory — distinct
from cross-session memory (Section 9). It captures the decisions that
shaped a tool: why this approach, what was tried and discarded, what
broke and how. Future-you (or future-LLM) reads this when picking up
work months later.

## Section 7 — Code Environment Protocol

```markdown
## 7. Code Environment Protocol
- **Always use a virtual environment** (`.venv/`) per project directory.
- **Pin dependencies** in `requirements.txt` with exact versions.
- **All packages from default upstream** (e.g., PyPI for Python, npm for
  Node). No custom mirrors without explicit operator approval.
- **System interpreter:** [your version, e.g., `python3.12`]
```

**Why this section.** Reproducibility. Version drift is the #1 source of
"it worked yesterday." Pinning dependencies + isolating environments means
the agent can't silently change what your code runs on.

## Section 8 — Working Style (Standing Instructions)

```markdown
## 8. Working Style
- **Take your time.** Correctness over speed.
- **Be curious and ask questions,** even tangential ones. Domain understanding
  leads to better output.
- **Propose your approach in plain language before writing code.** Catch bad
  plans before implementation.
- **When something fails twice, flag it and propose alternatives.** Don't
  keep iterating on a broken approach.
- **Update audit / review docs alongside the tools they cover.** Don't let
  documentation drift behind code; keep up with what's happening under the
  hood as it happens, not as a separate cleanup pass.
- **Build for portability.** Confirm code and schemas don't lock in to a
  single provider, format, or environment. Anti-fragility: every layer of
  the stack should be replaceable when the world changes.
- **Prioritize sense-making in all tasks.**
```

**Why this section.** This is the section operators forget to write — and
it's the section that most shapes the partnership. LLMs default to
"helpful, fast, agreeable." That defaults to *shallow*. Telling the agent
explicitly to slow down, ask, and disagree changes its behavior measurably.

**Specific patterns worth including:**
- **"Plain-language proposal before code"** stops bad plans early.
- **"Fails twice → flag and propose alternatives"** stops doom-loops.
- **"Disagree openly, no sycophancy"** — if your agent supports it.
- **"Update wiki / review docs alongside the tools"** — keeps audit trails
  current with what's happening under the hood. Documentation that lags
  code is documentation that lies.
- **"Confirm portability of code and schemas"** — always work toward
  anti-fragility. Code or schema bound to a single provider, format, or
  environment is brittle by design. The methodology's core defense is
  plain text on a filesystem (per `KNOWN_LIMITATIONS.md` cost portability);
  apply the same principle inside your tools.

## Section 9 — Session Memory Protocol

```markdown
## 9. Session Memory Protocol
- **Start of session:** Read `MEMORY.md` from your vault's auto-memory
  directory (path varies by harness) to restore context.
- **End of session (or after milestones):** Update `MEMORY.md` with current
  project state, files created/modified, key decisions, and next steps.
- **Missing memory directory:** Create it and initialize `MEMORY.md`
  immediately. Never silently skip memory.
- **Size limit:** Keep `MEMORY.md` under 200 lines (auto-load truncation).
  Use separate topic files for detail.
- **Content:** Stable facts — project state, design decisions, file
  inventory, open questions, next steps. Not transient session chatter.
```

**Why this section.** Memory is the difference between "a clever assistant"
and "a colleague who remembers." See `...MEMORY_SCHEMA.md` for the full
architecture. This section just guarantees the agent loads memory at the
start and updates it at the end.

## Section 10 — Edit Protocol

```markdown
## 10. Edit Protocol
This file is edited by both Operator and LLMs. Sign new entries.
When deleting for debugging/error correction, no archive needed.
When deleting to reorganize, copy deleted lines to `ARCHIVE.md` with
signature and timestamp before proceeding.
```

**Why this section.** This file lives a long time. Multiple editors
(operator + LLMs over many sessions) will touch it. Without an edit
protocol, history gets lost. Signing entries + archiving deletions
preserves the trail.

- *It is **critical** to have a known hierarchy when deploying multiple agents/multiple operators into your Protocol Schema.*

## What this directive replaces (and doesn't)

**Replaces:**
- Per-conversation context-setting ("remember, I'm a...")
- Re-explaining standing rules every session
- Hoping the agent will infer your guardrails from naming

**Does NOT replace:**
- `MEMORY.md` (cross-session topic memory)
- `MAINTENANCE_LOG.md` (per-tool decision log)
- `TASK_QUEUE.md` (current work)

The directive is the *contract.* The other files are the *content.*

## Token cost note

Auto-loaded files are paid in tokens at every conversation turn. A 500-line
directive costs ~5K tokens × N turns × every conversation. Rule of thumb:
*be ruthless* about what goes here vs. what goes in linkable docs. The
directive should be the spine, not the encyclopedia.

Concrete budget guidance:
- **Aim for under 200 lines** in the active directive.
- Push detail into `GOVERNANCE.md`, `MEMORY_SCHEMA.md`, etc., and link.
- Anything domain-specific that's not contract-level → memory topic file
  or per-project doc.
