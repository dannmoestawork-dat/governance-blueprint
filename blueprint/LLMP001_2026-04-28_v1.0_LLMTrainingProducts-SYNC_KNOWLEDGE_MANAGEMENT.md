> **Purpose.** Define the "Knowledge Management" layer — the directory
> where *validated* processes live, distinct from feedback memories
> (corrections still being learned), the per-tool MAINTENANCE_LOG
> (decision history per tool), and the code-review wiki (audit-time
> patterns). KM is the carved-in-stone layer: processes that have
> been used enough times that they're ready to be canonical.

> **KM vs. the Software Spec / `GOVERNANCE.md`.** Reasonable confusion.
> Both are "carved in stone." Both are operator-signed. The difference
> is **what they govern**: `GOVERNANCE.md` is *the rulebook* —
> classification tiers, HITL gates, what the agent may and may not
> touch, constraints on data movement. KM is *the validated processes
> the rulebook authorizes* — how you actually do session protocols,
> deployment runbooks, pricing, variance validation. **Governance
> defines the constraints; KM contains the playbooks that operate
> within them.** Two analogies: a constitution vs. an operations
> manual. A safety code vs. a procedure manual. They're peers, not
> overlaps. See "How KM relates to other persistence layers" below for
> the full layer map.

## Why this layer exists

The methodology has *several* persistence layers. Without a separation
between them, everything blurs. KM is what makes the difference between
"this is something we tried once and liked" and "this is the way we
work."

The four layers:

| Layer | Examples | Status |
|---|---|---|
| **Topic memories** (`feedback_*.md`, `project_*.md`, etc.) | Corrections, in-flight project context, references | *Provisional* — true at the moment, may evolve |
| **MAINTENANCE_LOG.md** (per-tool) | Why this script exists, what alternatives were considered, errors hit | *Per-tool* — durable per directory but not generalized |
| **Code-review wiki** (`Code_Review/patterns/`) | Reusable code or methodology idioms surfaced during audits | *Audit-time* — recognized after-the-fact |
| **Knowledge Management** (`Knowledge_Management/`) | Validated processes ready to be canonical | *Carved in stone* — promoted, audited, signed-off |

KM is the highest-trust layer. Everything in KM has been **used,
validated, and signed off** — at minimum by the operator, sometimes
also by external review.

## What belongs in KM

A KM entry meets all five criteria:

1. **Validated through use.** Not "we should do this"; "we've done this
   N times and it works."
2. **Generalizable.** Applicable beyond a single tool or project.
3. **Stable.** The shape of the process isn't changing every session.
4. **Operator-signed.** The operator has explicitly marked it ready.
5. **Portability resolved — harness-agnostic where possible, dependencies
   explicitly named when not.** Per `DIRECTIVE.md` Section 8 (Build for
   portability / anti-fragility), every KM entry must be honest about
   what it relies on. Two acceptable shapes:
   - **Harness-agnostic** — the process works regardless of which agent
     harness you're using. Preferred.
   - **Harness-bound, with named dependencies** — the process *does*
     rely on a specific harness feature (e.g., "uses Claude Code's plan
     mode," "uses an MCP server with capabilities X and Y"). The
     dependencies are spelled out at the top of the file so a future
     adapter can swap them.

   The criterion is **not** "the process must port unchanged to any
   harness" — that's unrealistic for genuinely useful tooling-specific
   work. The criterion is **"the dependencies are made visible"** so
   the operator can replace them when the harness changes. Hidden
   harness lock-in is the failure mode the criterion guards against.

Concrete examples (from real operator vaults):

- A **session protocol** — the start/end-of-session loops the agent
  runs.
- A **pricing model** — the formula the operator uses to price work.
- A **variance protocol** — how repeatability claims get validated
  before the tool ships.
- An **approved security pattern catalog** — patterns the operator has
  signed off as standing exceptions to default governance.
- A **VPS deployment runbook** — the steps for taking a tool live.
- A **gitignore standard** — the operator's canonical exclusion list.

Each of these started as a memory, a `MAINTENANCE_LOG` decision, or a
maintenance pattern. Each was promoted to KM after enough use that it
was *the* way, not *a* way.

## What does NOT belong in KM

- **Anything still being figured out.** Stays in `feedback_*.md`,
  `project_*.md`, or `MAINTENANCE_LOG.md` until validated.
- **Tool-specific decisions.** Stay in that tool's `MAINTENANCE_LOG.md`.
  Promote only the *generalizable* aspects to KM (and even then, the
  tool's log remains the decision record for that tool).
- **Code idioms.** Belong in `Code_Review/patterns/` — surfaced during
  audit, not promoted as process.
- **Session ephemera.** Conversation context, current-task state.

If you're not sure whether something belongs in KM: don't put it
there. The promotion gate is intentionally high-friction.

## The promotion gate

A topic memory or MAINTENANCE_LOG decision becomes a KM entry through
this gate:

1. **Use validation.** The pattern has been applied successfully N
   times (you pick N — typically 3–5). N=1 isn't validation; it's a
   first run.
2. **Generality check.** Does this apply beyond the original context?
   If only to one tool, it stays in that tool's log.
3. **Stability check.** Has the pattern stopped changing? If it's still
   evolving session-to-session, it's not ready.
4. **Operator sign-off.** The operator explicitly approves promotion.
   In the file, this is a status marker:
   - `[DRAFT]` — proposal phase, not yet operator-signed
   - `[CONFIRMED-BY-OPERATOR]` — promoted, durable, default rule
5. **Index entry.** Add a one-line pointer in `KM_INDEX.md`.

Demotion is also legitimate. If a `[CONFIRMED]` process turns out to
fail under load, demote it back to draft, fix, re-validate, re-promote.
Don't pretend it's still canonical when it isn't.

## File format

Each KM entry follows this shape:

```markdown
# [Process name]
## Classification: Tier [N]
## Status: [DRAFT | CONFIRMED-BY-OPERATOR]
## Confidence: [DRAFT | VALIDATED | EXTERNALLY-REVIEWED]

### What This Is
[1-3 sentences on what the process is and what it produces.]

### Why This Exists
[The trigger / motivation. What drove this becoming a standing process,
not just a one-time decision.]

### Source / How We Know
[The validation trail. What sessions, what tools, what cross-checks
established this works.]

### The Process
[Step-by-step. Numbered. Specific enough to be reproduced.]

### When To Apply
[The conditions that trigger this process. What inputs / contexts.]

### Opposing Steel Man
[The strongest case AGAINST this process. The cost. Operator-honest
acknowledgment that the process isn't free.]

### Maintenance
[When to revisit. Cadence in `SESSION_ENV.md` if applicable.]

---

_Signed: [operator] — [date promoted]_
```

The "opposing steel man" section is load-bearing. Validated processes
that don't acknowledge their cost ossify and rot. Forcing the steel
man at promotion time keeps the operator honest.

## `KM_INDEX.md` — the always-loaded entry point

Like `MEMORY.md` for memories, `KM_INDEX.md` is the always-loaded
entry point for KM. The agent reads it at session start to know what
canonical processes exist.

Format — same as `MEMORY.md` index:

```markdown
# KM_INDEX.md — Validated Processes

- [Session Protocol](session_protocol.md) — start/end-of-session loops
- [Variance Protocol](variance_protocol.md) — N-run repeatability for ship-quality claims
- [Pricing Model](pricing_model.md) — operator's pricing formula
- [Approved Security Patterns](approved_security_patterns.md) — standing exceptions to default governance
- [New Tool Build](new_tool_build.md) — checklist for spinning up a new tool directory
```

One line per entry. Pointer to file. Specific hook. Same hygiene rules
as `MEMORY.md`: under ~150 chars per line, organize by topic.

## How KM relates to other persistence layers

**KM vs. memory.** Memory is *what the agent should consider when
relevant*. KM is *the way you work*. Memory entries can be loaded
selectively; KM entries are read by the agent at session start when
the index points at them. Both live on the filesystem; both auto-load
their indexes.

**KM vs. MAINTENANCE_LOG.** A MAINTENANCE_LOG entry says "this tool
exists for this reason." A KM entry says "this is *the way* this
class of work gets done across all tools." When a MAINTENANCE_LOG
decision generalizes — same approach worked across three tools — it
gets a KM entry, with the original logs cross-referencing.

**KM vs. code-review wiki.** Code-review wiki entries are *patterns
recognized during audit*. KM entries are *processes followed
deliberately*. Some patterns surfaced in audit later become KM
entries (the wiki entry stays as the audit record; KM is the standing
process); some KM entries get audited and refined via code-review
sessions.

**KM vs. DIRECTIVE.md.** The directive is a *contract*. KM is *the
processes the contract authorizes*. The directive says "follow the
session protocol"; KM says "here's what the session protocol is."
Directive lines are short; KM entries are full step-by-step processes.

## Worked example — promoting a process

Real-world example:

1. **Session 1 (initial).** Operator hits a problem (memory and current
   state disagree on a measurement). The agent stops, the operator
   resolves it. Saved as `feedback_validate_then_update.md` in topic
   memory.
2. **Sessions 2–4.** Same pattern surfaces in different contexts. Each
   time, the feedback memory gets reused successfully.
3. **Audit (Code Review session).** The pattern is named in
   `Code_Review/patterns/P12_validate_then_update.md` as a recurring
   discipline.
4. **Promotion to KM.** After enough use, the operator marks the
   process for promotion. A new file
   `Knowledge_Management/validate_then_update.md` is written with
   `Status: [CONFIRMED-BY-OPERATOR]`. Cross-references back to the
   feedback memory (origin) and the wiki pattern (audit recognition).
5. **Index entry.** `KM_INDEX.md` adds:
   `- [Validate Then Update](validate_then_update.md) — when docs disagree, update toward better validation AND retest`

The original feedback memory stays — it's the *origin record*. The
wiki pattern stays — it's the *audit record*. KM has the *current
canonical process*. Three layers, three purposes.

## Anti-patterns to avoid

**Premature promotion.** Marking something `CONFIRMED` after one
successful use. Validation requires N. Don't pretend.

**The kitchen sink.** Putting every process you've ever followed in
KM. KM is the *load-bearing* processes; routine work doesn't belong.
If the index passes ~30 entries, you're probably over-promoting.

**The carved-and-forgotten.** Promoting to KM and never revisiting.
KM entries that haven't been read or referenced in a year are either
load-bearing-but-stable (good) or dead processes that need demotion
(bad). The cadence in `SESSION_ENV.md` should include a quarterly
"KM relevance scan."

**The contract substitute.** Trying to put governance rules in KM.
Governance is in `GOVERNANCE.md`; KM is for processes the governance
authorizes.

## Why this layer is named

Across operator vaults the directory is most often called `KM/` or
`Knowledge_Management/`. The naming acknowledges this is a librarian's
discipline: *what's the canonical record of how we do things*. Every
mature methodology develops this layer; naming it explicitly stops it
from becoming "the leftover folder."

---

## Maintenance

- **At promotion:** add `KM_INDEX.md` pointer, write the file with
  required sections, sign and date.
- **Quarterly:** scan KM for unused entries (haven't been referenced
  in a year). Demote candidates.
- **When a `CONFIRMED` process fails under load:** demote to `[DRAFT]`,
  fix, re-validate. Don't preserve canonicity for its own sake.
- **When a related memory or wiki entry exists:** cross-reference both
  ways. KM file points back to origin; origin points forward to KM.
