## 1. The problem this solves

*(Why this section: adopters conflate "the model improves" with "my system improves." The
distinction is the entire method.)*

A local model is a fixed artifact — it does not learn from your sessions. What CAN improve is
everything around it: the persistent prompt, the task specs, the validation gates, the context
scaffolding, the model configuration, and the output schemas. Local models are also unreliable
narrators about their own performance: the same model and instructions can produce clean
output, truncation, or confident fabrication depending only on framing and randomness.

Two rules follow, and everything else in this module is machinery for them:

1. **Improvement lands in structure, never in instructions.** A principle loaded is not a
   principle obeyed.
2. **Improvement is judged outside the model.** A deterministic grader script — never the
   model, and never your impression — decides whether a change worked.

## 2. The loop

```
1 MEASURE → 2 CAPTURE → 3 DISTILL → 4 GATE (human) → 5 APPLY → 6 RE-EVAL ─┐
    ▲                                                                      │
    └──────────────────────────────────────────────────────────────────────┘
```

| Station | Action |
|---|---|
| 1 MEASURE | Run versioned eval tasks (blind variant framings, deterministic grader) against a pinned config. |
| 2 CAPTURE | File every FAIL/PARTIAL as a typed Finding record. |
| 3 DISTILL | Turn a finding into a Proposal targeting exactly ONE lever, naming its proof-eval in advance. |
| 4 GATE | The operator approves by editing the proposal's status field. Never automated. |
| 5 APPLY | Make the edit; bump the config version. |
| 6 RE-EVAL | Re-run the named eval blind. Delta or revert. A proven win gets a regression eval — the ratchet. |

*(Why the human gate is non-negotiable: a self-modifying system with an automated approval
gate will eventually modify itself through a seam in that gate. Every mechanical gate has
seams; the operator's signature is the one that doesn't.)*

## 3. The six levers

L1 SOUL (persistent prompt/principles) · L2 SPEC (task directive) · L3 GATE (grader/validator
code) · L4 SCAFFOLD (context assembly) · L5 CONFIG (model tag, context window, quantization,
local-vs-cloud routing) · L6 SCHEMA (typed output contracts). One lever per proposal — that is
what makes deltas attributable. L7 (fine-tuning weights) unlocks later: the loop's ledger of
graded runs and typed failures is exactly the dataset fine-tuning needs.

*(Why the ordering discipline matters: when a run fails, classify the cause as spec-ambiguity
or grader-defect BEFORE model-error. Field experience: a large share of "the model failed"
turns out to be an ambiguous spec — fix the spec, re-run, converge — or a grader whose ground
truth was shallower than the model's output.)*

## 4. The ledger (the record schema)

A directory of append-only markdown records — see `templates/RECURSIVE_IMPROVEMENT.md` for
the copy-ready scaffold:

- `CONFIG_MANIFEST.md` — versioned definition of the build (model, ctx, prompt version, gate
  versions). Every applied change bumps `config_id`.
- `evals/EVAL-###.md` — task + blind variants + grader path + *dated ground-truth verification*
  + done-checklist + PASS/PARTIAL/FAIL rubric.
- `RUNS.md` — one row per graded run: date · eval · config · variant · run# · verdict ·
  evidence path · finding ref.
- `findings/F-###.md` — one failure, typed (spec-ambiguity | grader-defect | scaffold-gap |
  model-error | gate-blind-spot | config-limit) + lever hypothesis.
- `proposals/P-###.md` — one change, one lever, proof-eval named in advance, rollback line,
  human-edited status field.
- `evidence/` — raw model outputs, verbatim.

The model may read the ledger; only the operator writes it.

## 5. Boundary with the existing methodology

*(Why this section: three existing docs own adjacent territory; this module must compose with
them, not compete.)*

- **vs `KNOWLEDGE_MANAGEMENT.md` (the KM promotion gate):** KM promotes *validated knowledge* —
  a human decides a process is proven and carves it in stone. RSI proves *capability changes* —
  a grader decides a configuration is better. They chain: a proven RSI improvement that
  stabilizes into practice is then a KM promotion candidate. Never let the model's output be
  the promoting authority in either.
- **vs `MEMORY_SCHEMA.md` (the curation loop):** memory curation is "write → use → notice
  failure → fix" for *context*. RSI is the same shape for *capability*, with a mechanical
  judge. Keep the ledgers separate.
- **vs `GOVERNANCE.md` tiers:** an RSI loop over Tier 4–5 data is precisely the "data never
  leaves the machine" scenario the tiers were built for — the loop inherits the tier of the
  data its evals touch, and the §6a downgrade gate applies to publishing any eval material.
- **vs `SESSION_PROTOCOL.md`:** an improvement cycle is a *session type*, run deliberately
  (weekly is a good default), not a background daemon.

## 6. Minimal start (one afternoon)

1. Copy `templates/RECURSIVE_IMPROVEMENT.md` into your vault as `improvement/`.
2. Pin `C-001`: your current model tag, context length, prompt version.
3. Write EVAL-001 from a real task you already know the right answer to; write its grader
   (30 lines of Python is typical); verify the ground truth.
4. Run it blind, 2–3 variants. Grade. Log rows.
5. File your first finding. You now have a loop.

The step-by-step operating procedure (including the two-machine variant: authoring workstation
and inference box) is not part of this public release. Build yours as a runbook per
`RUNBOOK_METHOD.md`, starting from the five steps above.
