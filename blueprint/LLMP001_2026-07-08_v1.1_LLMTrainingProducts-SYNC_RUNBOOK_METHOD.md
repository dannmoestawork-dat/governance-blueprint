# RUNBOOK_METHOD — the live-history runbook: instructions + audit trail in one file
## Classification: Tier 0 (public methodology)

## 1. What a runbook is

One markdown file that is **both the instructions and the live record** of a multi-step
procedure or artifact build. The agent writes steps up to the next gate; the operator runs
them and pastes real outputs back into the file; the file accumulates the audit trail as the
work happens. When the procedure spans two machines (workstation ⇄ inference box / server),
the runbook is the membrane protocol: every command block is labeled with the machine it
runs on.

Why this shape earns its keep:
- **History** — the file IS the audit trail: every command, every real output, dated.
- **Copy-correctness** — one command per fenced block; the operator copies from the file,
  never from a chat window (chat soft-wraps long lines and severs the paste).
- **Cold-start handoff** — a status bar at the top means either party reopens the file and
  knows what's next without scanning.
- **Packageability** — a file-based, gated procedure is something you can hand a client or a
  future operator; a process that lives in a chat session is not.

## 2. Required skeleton (order fixed)

1. Title + classification + provenance tag
2. **STATUS BAR** — three lines, rewritten on every edit:
   `▶ YOU ARE HERE` · `🔴❓ OPEN QUESTIONS: <n>` · `🕒 LAST RESULT`
3. What this does (1–3 lines)
4. Operating rules (machine labels, copy/paste rule)
5. **▶▶ NEXT ACTIONS — DO THESE NOW** (the current block, lettered A→B→C)
6. **Stages** — the full procedure, numbered; gates marked ⛔; each stage has an `ACTUAL:` slot
7. 🔴❓ OPEN QUESTIONS (gathered list)
8. **Code Files** — every file the runbook produces or drives, by absolute path
9. **Wiki Aspect** — what this procedure teaches, written for a future outsider
10. **Run History** — dated one-liners

**Command-block format:** every block carries (a) a machine tag, (b) a one-sentence
`**Why:**` line directly above the fence, (c) exactly ONE self-contained command inside the
fence (carry its own `cd`/context so it can't misfire from the wrong directory). Multi-command
steps split into lettered sub-steps. When a procedure pauses mid-stream, a single inline
`> ▶ YOU ARE HERE` blockquote sits above the next command to run, and moves as steps complete.

**Symbols (fixed):** ▶ current action · 🔴❓ question blocking a gate · ⛔ output gates the
next step · ✅/❌ verified pass/fail · ⚠ caution · `ACTUAL:` the live-log slot for real output.

**The working loop:** agent writes as many steps as can run *without* an output deciding the
next one; the moment an output changes what comes next, that's a ⛔ gate — stop there. The
operator works the block, pastes outputs, answers 🔴❓; the agent folds results into
`ACTUAL:` + Run History and extends the next block.

**Scope:** every multi-step procedure AND every artifact build gets a runbook, living in the
project's own directory (`<THING>_RUNBOOK.md`) — including builds the agent runs entirely
itself (it fills the `ACTUAL:` slots with its own real outputs). Trivial one-liners are
exempt unless they produce an artifact you keep.

## 4. How this composes with the v1.0 docs — read this before adopting

*(Why this section: the runbook overlaps territory three v1.0 docs already own. These are the
reconciliation rulings, so adopters get ONE answer, not two.)*

- **vs `KNOWLEDGE_MANAGEMENT.md` (the collision that matters).** KM entries and runbooks are
  *different lifecycle stages of the same knowledge*. The **runbook is the live instrument** —
  written before/during the work, accumulating real outputs and decisions. The **KM entry is
  the distilled monument** — written after a procedure has been run enough times to be
  canonical, in the KM format (What This Is / Why / The Process / When To Apply / Opposing
  Steel Man). Rule: **work happens in runbooks; validated distillations get promoted to KM.**
  A KM entry may link its source runbooks as evidence. Where v1.0 text calls a KM entry a
  "runbook" (e.g. the VPS-deployment example), read it as a KM *distillation of* a runbook.
- **vs `GOVERNANCE.md` HITL gates.** No competition — different layers. Governance's tier
  table decides **WHETHER** an action needs human sign-off; the runbook's ⛔ marks **WHERE in
  the procedure** that sign-off (or any output-dependent stop) occurs. Every governance-
  required HITL moment inside a runbook procedure MUST surface as a ⛔ line; a ⛔ may also
  mark a purely mechanical stop (an output that decides branching) with no governance
  meaning. The approval-signal phrases ("go ahead", "ship it") remain the operator's spoken
  interface; the runbook records them in the `ACTUAL:` slot.
- **vs `MAINTENANCE_LOG.md` / `SESSION_ENV.md`.** Keep all three; they answer different
  questions. Runbook = "how do I run this procedure and what happened each step?" (per
  procedure). MAINTENANCE_LOG = "what do I know about this tool?" (per tool: errors, deps,
  reasoning). SESSION_ENV = "what happened across sessions?" (per vault). A runbook's Run
  History does NOT replace the MAINTENANCE_LOG — a tool-level lesson learned inside a runbook
  still gets its MAINTENANCE_LOG entry.
- **vs `TASK_QUEUE.md`'s single-writer rule.** TASK_QUEUE instructs the operator never to
  edit files while the agent runs. The runbook is the *deliberate exception*: it is a
  **turn-based two-writer file** — agent writes steps, then stops; operator fills `ACTUAL:`
  slots, then hands back. Never both at once; the STATUS BAR says whose turn it is. All other
  files keep the single-writer rule.

## 5. Adoption path

1. Copy `templates/RUNBOOK_METHOD.md`; write your first runbook for a procedure you already
   run by hand (a deploy is ideal).
2. Run it once, filling every `ACTUAL:` slot with real output — resist summarizing.
3. When a step misfires, fix the runbook (the step, the Why line, the gate placement) — the
   file, not the operator, is what improves.
4. After the procedure has run clean repeatedly, distill a KM entry and link the runbook.
