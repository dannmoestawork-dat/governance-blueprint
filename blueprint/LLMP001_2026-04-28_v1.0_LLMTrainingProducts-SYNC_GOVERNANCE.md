## How to use this document

Three ways:

1. **As a standing reference** — the agent reads this alongside the directive
   and applies the rules.
2. **As a per-task template** — copy Sections 1–6 into a task brief when
   assigning new work; the agent fills in the rest from standing directives.
3. **As an audit trail** — every artifact gets a classification header.
   You can grep your vault to confirm nothing is mis-classified.

**Relationship to DIRECTIVE.md.** The directive defines *who you are and
how you work*. This document defines *how you govern what gets built*.
If they conflict, the directive wins.

## 6. HUMAN-IN-THE-LOOP (HITL) GATES

For each task, define:
- **Gate points:** Where must the agent stop and wait for operator input?
- **Approval signal:** How does the operator say "go"?

Standing HITL gates:

| Action | Gate Required? | Why |
|---|---|---|
| Approved in-progress work (same project) | No | Standing authorization |
| New project / new directory | **Yes — plan mode** | Operator approves scope |
| External-facing deliverable | **Yes — explicit review** | Trust |
| Pricing / sensitive numerical inputs | **Yes — operator validates** | Field knowledge required |
| File deletion / destructive ops | **Yes — always** | Irreversible |
| Overnight autonomous work | No (if approved project) | Operator authorized this |
| Sending data externally | **Yes — always** | Privacy / trust |

Approval signals (template — pick what fits your harness):
- In chat: "go ahead", "do it", "approved", "ship it", "gtg"
- In `TASK_QUEUE.md`: moving a task from `[ ]` to `[>]`
- In plan mode: explicit approval prompt

### 6a. Classification Downgrade Gate

**Trigger:** Any action that moves data from a higher classification level
to a lower one (e.g., Tier 5 → Tier 4, Tier 4 → Tier 3, Tier 3 → Tier 2).
This includes:
- Writing higher-level data into a file, database, or context classified
  at a lower level.
- Deploying internal tools to an externally-accessible environment.
- Embedding sensitive data in output destined for a wider audience.
- Any operation that makes data accessible to a broader audience than
  its current classification permits.

**While all data remains at its current level or higher, standing
authorization applies.** The gate fires only on downgrade.

**When triggered, the agent MUST pause and explain:**
1. **What:** What data is moving and from which level to which level.
2. **Why this triggers a gate:** Which classification boundary is crossed.
3. **Risk:** What's the worst case if this goes wrong or leaks.
4. **Mitigation:** What safeguards are in place or proposed.

**The operator either:**
- **Approves this instance only** — agent proceeds, asks again next time.
- **Approves the pattern** — "This is fine going forward for all cases
  like this." Agent logs the approved pattern and does not re-ask for
  matching situations.

**Approved patterns are logged in:** `KM/approved_security_patterns.md`
(or whatever you name your knowledge-management directory) — with date,
description, operator's reasoning, scope of approval.

**Pre-deployment gate:** Before ANY tool or system goes live (accessible
outside this machine), a full Tier 0–Tier 5 summary review is required.
Operator and agent walk through every data element, its classification,
and confirm nothing has been inadvertently downgraded.

### Tier 0–Tier 5 — The 6-Level Classification System

| Level | Tag | Audience | Description |
|---|---|---|---|
| **0** | `Tier 0` | Public | Marketing, free education. Anyone can and should see this. |
| **1** | `Tier 1` | Qualified Lead | Gated content — trade for contact info + light screening. "Should we work together?" |
| **2** | `Tier 2` | Customer / Client | Full tool suite, databases, expanded education. Active service delivery. |
| **3** | `Tier 3` | Partner | Selective behind-the-scenes access. Strategic alliance level. |
| **4** | `Tier 4` | Internal | Shared with directs and your organization's umbrella. |
| **5** | `Tier 5` | Operator Only | Strategy, margins, IP, financials. Executive access. (Agent included by necessity.) |

**Adapting tier semantics to your domain.** The labels above describe a
small consultancy. Adapt to your context:

- *Academic researcher:* `Tier 0` = published; `Tier 2` = collaborators;
  `Tier 4` = lab notebook; `Tier 5` = pre-publication results.
- *Lawyer:* `Tier 0` = marketing; `Tier 2` = client matter file;
  `Tier 4` = firm work product; `Tier 5` = privileged strategy.
- *Independent consultant:* as the table above.

The *mechanism* (downgrade gate, classification headers, tier-specific
audiences) stays. The *labels* and *who's in each tier* you customize.

Classification rules:
- Every new file gets a classification header: `## Classification: Tier [N]`
- Default to the *highest* applicable level (classify up, not down).
- Downgrading a classification requires explicit operator approval.
- When in doubt, mark it Tier 4 (Internal) until the operator says otherwise.

## 8. COST & MODEL MANAGEMENT

For each task, consider:
- **Complexity:** Does this need a flagship model, or can a smaller one handle it?
- **Token budget:** Is the task token-heavy? Can it be chunked?
- **Offload candidates:** Repetitive formatting, bulk search, simple transforms.

Standing cost principles:
- Use the right model for the job (flagship for architecture/writing,
  smaller for simple search/formatting).
- Parallelize independent operations to reduce wall-clock time.
- Don't over-engineer — minimum viable solution first, then iterate.
- Subscription-based harnesses (e.g., Claude Code) are the primary tool;
  no additional API costs without explicit operator approval.

Future cost optimization targets:
- Local LLM (e.g., Ollama-hosted Llama / Mistral / Qwen) for repetitive
  formatting and data cleaning.
- Task routing: simple tasks → local model, complex tasks → cloud model.
- Token tracking per project for cost awareness.

## 9. DATA SANITIZATION

For each task involving sensitive data:
- **Identify:** What data in this task is identifying or sensitive?
- **Sanitize:** Replace real names/addresses with placeholders before
  external use.
- **Verify:** Confirm no PII in any external-facing output.

Standing sanitization rules:
- Names → `[Name]` in any published example.
- Addresses → `[Address]` in any published example.
- Numerical formulas with sensitive parameters → show structure, not actual values.
- Post-process: review all external-audience documents before release.

**Relationship to vendor/reference data:** Vendor specs and reference
materials may be proprietary but not secret — they're published to
authorized parties. You can reference them in deliverables. You cannot
republish them in a competing product.

## 10. DATA CURATION & ARCHIVAL

For each project, define:
- **Local storage:** Where do project files live within the vault?
- **Session data:** Temporary (conversation context) vs. durable (files on disk).
- **Retention:** How long do outputs stay? When do we clean up?

Standing archival practices:
- **Durable:** All project files in the vault (cloud-synced if applicable,
  with version history).
- **Session-temporary:** Conversation context expires; recover via `MEMORY.md`.
- **Cleanup triggers:** Project completion → archive to `_Archive/`
  subdirectory or delete if superseded.
- **Version history:** Cloud sync providers (OneDrive, Dropbox, Git) keep
  file versions automatically. Safety net for accidental overwrites.
- **Provenance tags** serve as the audit trail for who created what.

Future archival goals:
- Local encrypted archive (sovereign vault concept).
- Cloud session purge verification (confirm AI provider data retention compliance).
- Formal project sign-off process (e.g., a `#OPERATOR_ARCHIVED` tag).

## Why this is one document instead of fifteen

A common mistake: spreading governance across many short policy docs
the agent has to remember to load. That fails — auto-loaded files
multiply token cost; non-auto-loaded files get forgotten.

Instead, **GOVERNANCE.md is one document with eleven sections** and a
quick-reference template at the bottom. The agent loads it once at
session start (via the directive's link map) and references specific
sections by anchor. One file = one canonical contract.
