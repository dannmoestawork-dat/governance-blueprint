## The lifecycle ramp

The most load-bearing structural pattern is the **lifecycle ramp** in `Production/`:

```
_io/  →  Pipeline/Project_Pre_Plan/  →  Active_Projects/  →  (delivered)
```

| Stage | Directory | What it means |
|---|---|---|
| **1. Inflow** | `_io/<Operator>_io/Project_Details/` | Raw inputs land here unprocessed |
| **2. Pre-plan** | `Pipeline/Project_Pre_Plan/<project>/` | Working draft — agent + operator assemble required components |
| **3. Active** | `Active_Projects/<project>/` | Packaged, ready to send externally |
| **4. Out the door** | (sent / delivered) | No longer in the lifecycle; archive on completion |

**Why the ramp matters.** It maps abstract phases ("gathering," "drafting,"
"finalizing") onto folder paths the agent can navigate. The agent doesn't
need to ask "is this project ready to ship?" — the *path* says so.

**The "real work" definition.** A project lives in `Active_Projects/` only
when the tools that produced its deliverables are *reliable enough to send
externally*. Work-in-progress on the *tool itself* lives in `Tools/`,
not in this lifecycle. Once a tool is reliable, its outputs may flow into
`Active_Projects/` for a real client.

## Three views of the same vault

Different mental models help in different situations.

### View 1 — By Folder (annotated tree)

The annotated tree above. Use when you're locating something by structure
("where do scrapers live?").

### View 2 — By Workflow ("I want to...")

| I want to... | Go here |
|---|---|
| See open tasks | `TASK_QUEUE.md` (vault root) |
| See what tools exist | `INVENTORY.md` (vault root) |
| Understand the project | `START_HERE.md` if present, else `README.md` + `DIRECTIVE.md` |
| Find a finished deliverable | `Production/Active_Projects/<project>/` |
| Look up a reference | `Production/Reference/<system>/` |
| Find a validated process | `Knowledge_Management/KM_INDEX.md` |
| Review code quality | `Code_Review/WIKI.md` |
| See what's in the pipeline | `Production/Pipeline/Project_Pre_Plan/` |
| Check the directive | `DIRECTIVE.md` (vault root) |

### View 3 — Data Flow (which tool feeds which)

A diagram (in text) of how raw inputs flow through tools into the CRM and
out to deliverables. Specific to your domain — sketch yours when the layout
matures.

```
RAW INPUTS  →  PROCESSING TOOLS  →  CRM (relationship hub)  →  DELIVERABLES
```

Example pattern:
```
Reference data ──→ Tool/parse_*.py ──→ database ──→ CRM vault ──→ Active_Projects
External feeds ──→ Tool/scrape_*.py ──→ database ──→ CRM vault
Operator inputs ──→ Tool/build_*.py ──→ generated workbook ──→ Active_Projects
```

## Per-tool directory anatomy

Every directory under `Tools/` follows the same internal shape:

```
Tools/<Tool_Name>/
├── .venv/                  ← Per-tool virtualenv (gitignored)
├── requirements.txt        ← Pinned dependencies
├── MAINTENANCE_LOG.md      ← Per-tool decision log
├── <main_script>.py        ← Or main module
├── helpers/                ← Sub-modules
├── tests/                  ← Test fixtures
├── output/                 ← Where the tool writes its outputs
└── README.md (optional)    ← One-page user guide if the tool is non-trivial
```

The `MAINTENANCE_LOG.md` is the file you read when you pick up the tool
six months later and have forgotten what it does and why.

## Naming convention applied to folders

Folders generally follow simpler naming than files. Conventions:

- **Use underscores** for spaces in folder names: `My_Project/`, not `My Project/`.
  Some tools (especially Bash globbing, older Windows utilities, some Python
  packages) trip over spaces.
- **No special characters** in folder names. Stick to `[A-Z][a-z][0-9][_]`.
- **Use the project mnemonic prefix** for project subfolders if you have many:
  `RTK014_Example_Project/`, `LLMP001_TrainingProducts/`. (See `NAMING_CONVENTIONS.md`.)
- **Sync state suffix is optional on folders.** It mainly applies to files. If
  a folder *contains* mixed-state files, it inherits the most-restrictive tier
  for permissions purposes.

## Maintenance

When to update this file:
- New top-level directory added
- New tool/script created (also update `INVENTORY.md`)
- Data flow between tools changes

When NOT to update:
- Routine file additions inside an existing tool (handled by per-tool `MAINTENANCE_LOG.md`)
- Sub-folder reorganization within a single tool

Who updates: agent during a session, or operator between sessions. Either way,
sign and date the change in `ARCHIVE.md` if you're deleting or moving substantial
sections.

## Why a folder spec at all?

Two reasons:

1. **Token economics.** The agent needs to *find* things without scanning the
   entire vault. A predictable layout means the agent infers paths from
   intent — "the budget tool is under `Production/Reference/`" — and can
   open the right file in one shot.

2. **Operator continuity.** You'll forget where things are. Future-you won't
   remember why `Sub_Templates/` is under `Pipeline/` and not under `Tools/`.
   This document is the canonical answer.
