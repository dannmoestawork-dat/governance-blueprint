---

## Wait — is this our internal git system?

Fair question. **No, but they're complements, not substitutes.** They
record different facets of the same history:

| Layer | Records | Answers |
|---|---|---|
| **Git** (or any version-control system) | What changed and when, line-by-line, with the commit author | "What was different last Tuesday?" "Who introduced this line?" |
| **MAINTENANCE_LOG** | Why things are the way they are — decisions, alternatives considered, errors hit, dependencies pinned and the reason for pinning | "Why did we pick PyMuPDF over pdfplumber?" "Why is this dependency at v2.4.4 and not the latest?" |

Even with disciplined commit messages, decision rationale gets diluted
across hundreds of commits and goes long-tail unfindable. The
MAINTENANCE_LOG keeps load-bearing reasoning in one greppable place
*per tool*, indexed by section, easy to read end-to-end.

**This methodology works whether or not you use git.** The
MAINTENANCE_LOG is durable on its own — a flat-file decision record
that survives any version-control choice. If you do use git, the two
layer naturally: git for "what / when," MAINTENANCE_LOG for "why."

## Why this file exists

The codebase tells you *what* the tool does. Version control (if
you're using it) tells you *when* changes happened. The
MAINTENANCE_LOG tells you *why* — and that's the part that vanishes
from memory fastest.

Without a maintenance log:
- You re-debug problems that were already solved and forgotten.
- You re-litigate design decisions because the original reasoning
  didn't survive.
- New collaborators (or future-you) lose half a day reading code
  trying to reconstruct context.

The log is short. The log is durable. The log compounds.

## Required sections

Every MAINTENANCE_LOG.md has these four sections. In this order.

### 1. Error Log

Date-stamped entries for errors encountered during development.
Include: what failed, the root cause (if known), and what was done
to fix or work around it.

**What goes here:**
- Bugs that took >15 minutes to diagnose.
- Errors that surfaced architectural problems.
- Workarounds and the reason they were needed.
- "It worked, then it didn't, then it did" mysteries.

**What doesn't:**
- Routine syntax errors.
- Typos.
- "I forgot a comma."

### 2. Script & Approach Reasoning

Why each script exists, what alternatives were considered, and why
the current approach was chosen.

**What goes here:**
- "We considered X, Y, and Z. Picked Y because [reason]."
- Why a "weird" library choice was made.
- Why the file is structured this way and not the obvious other way.
- Why a "duplicate" exists (it's not a duplicate, here's the
  difference).

**What doesn't:**
- Standard explanations of well-known patterns.
- Restatement of what the docstring already says.

### 3. Dependencies

What libraries the tool needs, version constraints, where they're
installed.

**What goes here:**
- Pinned versions matching `requirements.txt` (or equivalent).
- Why a version is pinned (e.g., "0.x has breaking change in API X").
- System dependencies (e.g., "needs imagemagick installed via apt").
- Per-tool venv location.

**What doesn't:**
- Routine stdlib usage.

### 4. Session Handoff Notes

End-of-session summary: what's done, what's in progress, what the
next step should be.

**What goes here:**
- Last edit's purpose and outcome.
- What's left to ship before the tool is "done."
- Known limitations the next session should be aware of.
- The single most important thing future-you should know.

**What doesn't:**
- Conversation transcript.
- Day-by-day diary.

## Rules

- **Create when the first script is written** in a directory. Don't
  wait for a "real" need.
- **Update during development**, not just at the end. The log is
  only useful if it's current.
- **Tag entries** with `[AI-GENERATED]` / `[AI-ASSISTED]` / `[VERIFIED]`
  per the directive's provenance protocol.
- **Keep entries concise.** This is a decision log, not a narrative.
- **Date every entry.** ISO format (`2026-04-28`). No exceptions.
- **Sign every entry.** Operator signature or agent identity (e.g.,
  "Claude Opus 4.7"). Critical for trust trails.

## Worked example

Below is a partial example showing what real entries look like.
Copy the shape, not the content.

```markdown
# MAINTENANCE_LOG.md — [Example Tool: PDF Parser]
## Classification: Tier 4
## Started 2026-03-15

## Error Log

| Date | Issue | Root Cause | Resolution |
|------|-------|-----------|------------|
| 2026-03-22 | parser hung on certain PDFs | encrypted PDFs with zero-byte content streams | added try/except around content extraction; log + skip |
| 2026-04-03 | unicode crash on Windows | `cp1252` default codec couldn't encode Russian glyphs | force UTF-8 with `sys.stdout.reconfigure(encoding='utf-8')` |

## Script & Approach Reasoning

### 2026-03-15 — Why PyMuPDF over pdfplumber
[AI-ASSISTED] — Operator + Agent

Considered pdfplumber, PyMuPDF, pypdfium2, and unstructured.io.
Picked PyMuPDF because: (1) handles encrypted PDFs natively,
(2) ~10× faster on the 200-page test set, (3) layout extraction
preserves table structure for our use case. pdfplumber was the
runner-up but lost on speed.

### 2026-04-03 — Why we chunk at 50 pages, not whole-file
[AI-GENERATED] — Agent (Claude Opus 4.7)

Memory profiling showed >1GB peak on 500-page documents when
processed whole. Chunking at 50 pages keeps peak under 200MB
while adding only ~3% to total runtime. Tradeoff acceptable.

## Dependencies

| Library | Version | Purpose |
|---------|---------|---------|
| PyMuPDF | 1.27.2 | PDF parsing |
| Pillow | 12.2.0 | image extraction |
| numpy | 2.4.4 | tabular post-processing |

**Venv location:** `Tools/PDF_Parser/.venv/`

## Session Handoff Notes

### 2026-04-15 — End of session summary
[AI-ASSISTED] — Operator + Agent

- **Completed:** Encrypted-PDF handling, unicode fix, chunking optimization.
- **In progress:** Table extraction is 80% — handles simple tables,
  fails on multi-row headers.
- **Blocked on:** Need real-world examples of multi-row-header tables
  to test against. Operator collecting samples this week.
- **Most important thing for next session:** Don't refactor the chunking
  logic — it's load-bearing for the memory profile, and that profile
  was hard-won.
```

## Anti-patterns to avoid

**The narrative log.** Long-form prose. "Today I worked on the parser
and tried a bunch of things..." Useless. Use the structured sections.

**The omniscient log.** Written as if everyone knows the project. "Of
course we picked X." Future-you doesn't know "of course." Spell it out.

**The TODO list.** Maintenance log isn't a task tracker. Use
`TASK_QUEUE.md` for tasks. Use the maintenance log for *why* of decisions
already made.

**The marketing doc.** "This elegant solution leverages the latest..."
No. State what was built and why. No fluff.

**The silent log.** No entries between major releases. Means the log
isn't being updated during development — only at the end. By then,
context has decayed. Update during, not after.
