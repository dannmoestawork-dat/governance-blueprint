## Section 1 — Python libraries

Pick what you need. Most operators start with one provider SDK + a
filesystem and grow from there.

### Provider SDKs (cloud LLMs)

#### `anthropic`
- **Role.** Official SDK for Anthropic's Claude models. HTTP requests,
  streaming, tool-use, prompt caching, vision, batch.
- **When to reach for it.** When your code needs to call Claude
  programmatically (any custom agent, batch job, or scoring harness).

#### `openai`
- **Role.** Official SDK for OpenAI's GPT models. Same shape as
  `anthropic`: completions, tools, streaming, embeddings.
- **When.** OpenAI-specific features (e.g., fine-tuning their models, or
  consensus / cross-check of two providers on the same input).

#### `mistralai`
- **Role.** Official SDK for Mistral's hosted models.
- **When.** When you want a third provider for cost arbitrage or
  multi-model consensus, or when Mistral's specific features (e.g.,
  certain coding benchmarks) are what you want.

### Local model runners

#### `ollama`
- **Role.** A local LLM runner that downloads and serves open-weights
  models (Llama, Mistral, Qwen, Phi, Gemma, etc.) behind a clean HTTP
  API. Exposes `localhost:11434` by default.
- **When.** When data sovereignty matters (Tier 4–5 content shouldn't
  leave the machine), or when latency / cost matters for high-volume
  routine work, or when you want offline capability.

#### `llama-cpp-python`
- **Role.** Direct GGUF inference. Lower-level than ollama; you load
  the model file yourself and call inference directly.
- **When.** Sovereign-workstation builds where you want fine control
  over the runtime, or for embedded / edge deployments where ollama's
  daemon overhead is too much.

### Memory + retrieval infrastructure

#### `mcp` (Model Context Protocol)
- **Role.** A standardized protocol for exposing tools and resources
  to LLM agents. MCP servers speak a common JSON-RPC dialect; any
  MCP-compliant client can use any MCP-compliant server.
- **When.** When you want one tool definition (filesystem access,
  database queries, web fetch) to work across multiple agent harnesses
  without rewriting per-harness adapters.

#### `sentence-transformers`
- **Role.** Embedding models — turn a paragraph into a high-dimensional
  vector that captures meaning, so semantically-similar text has
  similar vectors.
- **When.** When you want *semantic* memory retrieval — "find the
  memory most relevant to this question" — beyond keyword match. Useful
  when your memory store grows past the size where the
  description-keyword-match approach in `MEMORY_SCHEMA.md` starts
  missing.

#### `chromadb` / `qdrant`
- **Role.** Vector stores. They ingest the embeddings from
  `sentence-transformers` and serve nearest-neighbor queries fast.
  ChromaDB is simpler and runs in-process; Qdrant is a separate
  service that scales further.
- **When.** When you've outgrown filesystem grep + the `MEMORY.md`
  index, and want the agent to find relevant context by semantic
  similarity rather than your descriptions matching its keywords.

### Document handling

#### `pymupdf` (`fitz`)
- **Role.** PDF parsing — text, images, vector primitives, page
  rendering to PNG. Fast and feature-rich.
- **When.** When your domain involves PDFs that the agent should be
  able to read (specs, contracts, drawings, papers).

#### `python-docx`, `openpyxl`
- **Role.** Word and Excel document generation / parsing.
- **When.** When deliverables go to clients or partners who use Office
  formats.

#### `obsidian-tools` (or equivalents)
- **Role.** Programmatic operations on Obsidian vaults — read frontmatter,
  resolve `[[wikilinks]]`, run dataview queries from outside the app.
- **When.** When you want scripts to read or write your vault directly
  without going through Obsidian's UI. Most useful for build scripts
  that generate vault files (e.g., a CRM that produces note files).

### Filesystem watchers

#### `watchdog`
- **Role.** Filesystem change events — get a callback when files in a
  directory are created, modified, or deleted.
- **When.** When you want the agent to react to file changes rather
  than poll. Common pattern: an `_io/` inflow directory where new files
  trigger an ingest pipeline automatically.

### What to install first

For most operators starting from scratch:

```bash
pip install anthropic                # or your provider of choice
pip install pymupdf                  # if you have PDFs
pip install python-docx openpyxl     # if you handle Office formats
```

That's enough to do real work. Add `ollama` when you want local
inference. Add `sentence-transformers` + `chromadb` when your memory
store grows past the size where keyword matching reliably finds the
right files.

## Section 2 — Obsidian setup

Obsidian is a markdown editor / vault browser that turns a folder of
`.md` files into a navigable knowledge base. The methodology in this
blueprint produces vaults that *are* Obsidian-compatible by default —
no migration required.

### What Obsidian is (and isn't)

- **A vault is just a folder.** No proprietary storage, no database.
  Your `.md` files stay readable in any text editor, any time, even if
  Obsidian disappears tomorrow.
- **Markdown is the format.** Frontmatter is YAML at the top of files.
  Standard markdown links work; Obsidian also supports `[[wikilinks]]`
  that resolve across the vault.
- **The "graph view" comes free.** Open a vault and Obsidian shows a
  network diagram of which files link to which. The methodology
  produces lots of inter-doc links, so the graph becomes a real
  navigation aid.

What Obsidian doesn't do: edit binary files, run code (without
plugins), sync (without iCloud / OneDrive / git / a paid Obsidian Sync
subscription).

### Recommended core plugins

Free, official, ship with Obsidian:

| Plugin | What it does | When to enable |
|---|---|---|
| **Templater** | Boilerplate / scaffolding for new files (frontmatter, naming convention prefixes) | Right away — saves 30 seconds per new file |
| **Dataview** | Query frontmatter across the vault, render results as tables / lists | When you have ~10+ similarly-shaped notes (e.g., projects, contacts) and want roll-up views |
| **Excalidraw** | Diagram-as-markdown — sketches saved as `.md` so they go through the same git / sync flow as everything else | When you need diagrams (architecture, flowcharts) in the same vault as prose |

Community plugins (curated, off-the-shelf):

| Plugin | What it does |
|---|---|
| **MCP-bridge** | Exposes the Obsidian vault as an MCP server, so MCP-compliant agents can read your notes through the protocol |
| **Tasks** | Aggregate `[ ]` checkboxes across the vault (your `TASK_QUEUE.md` becomes one of many task surfaces) |
| **Calendar** | Daily-note pattern, useful for session-end snapshots |

### How `MEMORY.md` becomes browsable

`MEMORY.md` is the memory index. In Obsidian:

- **Each `[Title](file.md)` link** becomes a clickable navigation point.
- **The graph view** shows `MEMORY.md` at the center with every topic
  file linked off it. Visualizes memory density and isolated nodes.
- **Wikilinks (`[[file]]`)** resolve to the actual file, so you can
  navigate the memory store without leaving Obsidian.

The agent doesn't *use* Obsidian. The agent reads / writes the same
`.md` files via the filesystem. Obsidian is the *human-facing* view
of the same data.

### How LLM-written topic files surface as graph-view nodes

Each `feedback_*.md`, `project_*.md`, `user_*.md`, `reference_*.md`
becomes a node in the graph. Patterns emerge visually:

- A topic file with many incoming links → load-bearing memory.
- A topic file with no incoming links → orphan; either consolidate or
  prune.
- Clusters → memories that reinforce each other (e.g., several
  `feedback_*` files all tagging the same domain).

This is the curation surface. Periodically, open the graph view, look
for orphans, look for clusters, decide what to merge or trim.

### Cold-start checklist

For an operator new to Obsidian:

1. Install Obsidian (free, single download).
2. Open your vault folder. (Adopt this methodology's `templates/`
   first; vault becomes your work directory.)
3. Enable Templater + Dataview from core plugins.
4. Skip community plugins until you have a need.
5. Don't worry about the graph view until you have ~20 files. Earlier
   it's just clutter.

## Section 3 — Agent tools — under the hood

This is the section operators most often skip and most often regret
skipping. When something goes wrong with an agent — a tool returns the
wrong shape, memory doesn't load, the agent "forgets" mid-conversation
— understanding the message-loop layer makes troubleshooting tractable
instead of magic.

### What tool-calling actually is

When an agent "uses a tool" (filesystem read, web search, database
query), here is what actually happens:

1. The model produces structured output indicating intent: *"call the
   `read_file` tool with path = `/foo/bar.md`."* This output is JSON-
   shaped, not natural language.
2. The **harness** (the runtime around the model — Claude Code, Cline,
   a custom Python loop) receives the tool-call request and **executes
   it** on the actual system. The model itself does not have file
   access; the harness has file access.
3. The harness sends the tool result back to the model as structured
   input.
4. The model continues its turn with the result in context.

The model is *deciding what tools to call.* The harness is *actually
calling them.* This separation is critical:

- The agent's permissions are exactly the harness's permissions. If the
  harness can't write to `/etc/`, the agent can't either. If the
  harness sandboxes the filesystem to your vault root, the agent
  cannot escape.
- "Tool use" is a contract: the harness decides which tools exist and
  what arguments they accept. The model picks among offered tools; it
  doesn't invent new ones.

### The message loop

A session is a loop:

```
loop:
  user_message → model_input
  model produces: text + tool_calls
  for each tool_call:
    harness.execute(tool_call)
    result → model_input
  model continues until: stop sequence | tool_calls exhausted
end loop
```

Each iteration of the loop adds to the context window. The model sees
every prior message + every tool result + every text turn. This is why
context windows matter — the loop accumulates state.

### Why memory must persist outside the context window

The context window is **finite** and **per-session**. The memory store
is **infinite** (filesystem-bounded) and **across-session**. Two
implications:

1. **Anything you want next session needs to be on disk.** The
   conversation context disappears when the session ends. Memory files
   survive.
2. **The auto-loaded files (`DIRECTIVE.md`, `MEMORY.md`) are the
   bridge.** They get re-injected at the start of each session, giving
   the next model instance access to the prior session's distilled
   state.

This is why `MEMORY.md` matters. It's the connective tissue between
sessions.

### How MCP standardizes tool exposure

Without MCP, every tool is harness-specific. You build a "read file"
tool for Claude Code; it doesn't work in Cline. You rebuild it for
Cline; it doesn't work in your custom Python agent. Three
implementations of the same tool.

MCP says: a tool server exposes its capabilities via a standardized
JSON-RPC protocol. Any MCP-compliant agent can connect to any
MCP-compliant server.

For the methodology: when you want to expose your vault to multiple
agents (Claude Code, a custom batch job, a future agent you haven't
chosen yet), build the tool as an MCP server once. Every harness gets
it.

### How filesystem / bash / web-search tools get sandboxed

The harness defines the sandbox. Common patterns:

- **Filesystem scope.** The harness only exposes paths under a specific
  root. The vault root is the natural fence.
- **Command allow/denylist.** The harness inspects bash commands before
  execution. Some commands (e.g., `rm -rf`) get auto-blocked or
  require explicit user approval.
- **Network policy.** Web-fetch tools may be allow-listed to specific
  domains, or rate-limited, or blocked entirely.
- **Per-action approval.** Some harnesses ask the user before *every*
  destructive action; others have standing approval for specific
  patterns.

The methodology's `GOVERNANCE.md` Tier 0–5 + HITL gates are the
**operator-side complement** to the harness's sandbox. The harness
enforces what *can* happen; governance defines what *should* happen.

### Token economics

Every token in the model's context window costs money (or, for local
models, latency). Auto-loaded files are paid in tokens **at every
turn** of every session.

Implications:

1. **Keep `MEMORY.md` lean.** It's auto-loaded every turn. A 500-line
   index costs ~5K tokens × every turn × every session. The 200-line
   limit isn't arbitrary — it's the point past which most harnesses
   start truncating.
2. **Push detail into topic files.** Topic files load only when the
   agent decides they're relevant. They're free until used.
3. **Output tokens cost more than input tokens.** Most providers price
   output ~3-5× higher. A long-output session is more expensive than a
   long-input session.
4. **Prompt caching matters.** When the same auto-loaded prefix
   repeats across queries, providers can cache it and charge a fraction
   of the per-token rate for cache hits. Anthropic supports this via
   `cache_control: ephemeral`. Worth ~90% cost reduction for
   high-frequency queries with stable system context.

### What this means for the methodology

- The seven primitives in this blueprint (Model / Obsidian /
  File_System / Markdown / Script / memory_schema / Naming convention)
  are designed to *work with* the message-loop architecture, not
  against it.
- Persistent memory + auto-loaded directive + per-session protocol is
  the methodology's response to the loop's per-session amnesia.
- Token economics is why memory hygiene (curation, index brevity, topic-
  file specificity) is load-bearing — every poorly-described memory
  file is a tax on every future query.

## Section 4 — Common operator patterns

Three patterns operators tend to discover after a few weeks. Naming them
upfront saves the rediscovery cost.

### Pattern 1 — Cloud + local hybrid

Use a cloud provider (Anthropic, OpenAI) for **complex reasoning**
where capability matters. Use a local model (ollama) for **bulk
formatting / classification / summarization** where the cheaper model
is good enough.

The `DIRECTIVE.md` can specify the cloud model; specific scripts can
hit the local model directly. Token economics drive this: most routine
work is fine on a 7B local model.

### Pattern 2 — MCP server per concern

Don't build a monolithic agent. Build small MCP servers, one per
concern (filesystem, vault search, database queries, web fetch). Wire
them into your harness. Each is independently testable / debuggable.

This is the agent-architecture analogue of "small composable functions
beat one big function."

### Pattern 3 — Prompt cache the auto-load layer

Anthropic's prompt caching gives ~90% cost reduction on cache hits.
The auto-loaded directive + memory index is *exactly* the kind of
content that benefits — same prefix every turn, different user content
each turn.

If you're running >100 agent queries a day, this is worth wiring up.
At lower volume, the implementation cost outweighs the savings.

## Section 5 — One viable infrastructure stack

> **Important framing.** What follows names specific tools the
> methodology's authoring vault uses. **This is not an endorsement —
> it's documentation of one working stack.** Substitute equivalents
> wherever your context differs. The point is to make the actual
> deployment pattern visible so you can adopt it, replace pieces,
> or reject it on informed grounds.

### Sovereign workstation hardware

A sovereign workstation is the long-term home for any operator who
wants Tier 4–Tier 5 work to live entirely on hardware they control.
Common builds: a desktop class workstation (32-128 GB RAM, GPU
sufficient to run open-weights models locally via ollama / llama-cpp)
plus an offsite VPS for services that need to be reachable from
multiple devices.

For the local box, any modern Linux distribution works. The methodology's
authoring vault runs on a small mix: a Windows + WSL/Git Bash desktop
for daily work, a future Linux workstation for sustained local
inference, and a Linux VPS for persistent services.

### Remote-access mesh — Tailscale

**Tailscale** is a WireGuard-based mesh VPN that lets you reach
machines you own from anywhere without exposing them to the public
internet. The methodology's authoring vault uses Tailscale to gate
remote access to a deployed agent service — the service binds to a
Tailscale-only IP, and only authenticated devices on the operator's
tailnet can reach it. No port-forwarding to the public internet, no
SaaS dependency.

Other viable options: Nebula, ZeroTier, plain WireGuard with manual
key management, or `ssh -R` reverse tunnels for narrower use cases.
Tailscale is named here because it's what the authoring vault uses,
not because the alternatives are worse.

### VPS — Hetzner

**Hetzner** is one of several reasonable VPS providers for hosting a
deployed agent service. The methodology's authoring vault runs a
self-hosted consultant LLM on a Hetzner VPS, gated behind Tailscale,
with `systemd` running the service.

Other viable options: Linode, Vultr, DigitalOcean, OVH, Hostinger,
or self-hosted hardware in a closet. The choice depends on cost,
data-residency requirements, and whether you want the provider in
your blast radius. Hetzner is named because it's what the authoring
vault uses; substitute any provider that meets your trust threshold.

### Domain-specific authoring tools — FreeCAD as one example

When the operator's domain produces structured artifacts (drawings,
diagrams, models, layouts) that the agent helps design, the agent and
operator need a shared authoring tool that can be driven both
interactively (operator clicks) and programmatically (agent edits).

**FreeCAD** is one example: an open-source parametric CAD tool with a
Python scripting layer. Agents can generate `.FCStd` files via the
Python API; operators can open and refine them in the GUI. This is
what the authoring vault uses for spatial-domain artifacts.

For other domains:
- **Diagram / flowchart authoring** → Excalidraw (in Obsidian),
  Mermaid (markdown-native), draw.io
- **Document authoring** → LaTeX + agent edits, Pandoc + markdown,
  Office formats via `python-docx` / `openpyxl`
- **Image / illustration** → Inkscape (SVG, scriptable), Krita
- **Code authoring** → IDE of choice + agent integration

The pattern: pick a tool with both interactive and programmatic
access. Avoid tools that only offer one. The agent must be able to
edit the artifact; you must be able to refine it.

### Why this section names specific tools

The methodology compounds when the operator's actual stack is
visible — naming concrete tools is honest and lets adopters either
match the stack (cheap path) or knowingly substitute (informed path).
Hiding the stack and writing in pure abstractions makes the
methodology look more general but actually weakens the worked
example: an adopter has to guess what real tooling looks like.

**Per the operator's own anti-fragility principle (`DIRECTIVE.md`
Section 8):** these tool names are dependencies in the
methodology's worked example. They're documented as such so a future
adapter can swap them without losing the methodology's structure.
