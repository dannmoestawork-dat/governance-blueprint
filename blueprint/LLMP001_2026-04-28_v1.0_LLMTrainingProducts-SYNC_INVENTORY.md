> **Purpose.** A catalog of every tool, script, database, and generated
> output in the operator's vault. Each entry says what it does, where
> it lives, how to run it, and what it produces.

---

## Why an inventory

Six months from now, the operator will type `ls Tools/` and see
twenty directories and not remember what half of them do. The agent
will scan the directory tree at the start of a long session and
spend five minutes orienting before doing useful work.

The inventory is the index that makes the toolset *navigable*.
It's also what teaches a new collaborator (or a new agent) what
exists and how to use it.

---

## Maintenance rule

**Update this file whenever a new tool is created or an existing tool
changes significantly.** Added to the end-of-session protocol so it
doesn't decay.

A tool not in `INVENTORY.md` is, for navigation purposes, invisible.
The only way the inventory stays useful is by being current.

## Template entry

Each tool gets a table with these fields:

```markdown
### N.M [Tool Name]
| Field | Value |
|---|---|
| **Script** | `path/to/main_script.py` |
| **Purpose** | (1-3 sentences on what the tool does and what problem it solves) |
| **Inputs** | (files, data, configuration the tool consumes) |
| **Outputs** | `path/to/output.xlsx` (one or more output files with paths) |
| **Venv** | `path/to/.venv/` |
| **Dependencies** | `lib==X.Y.Z, lib2==X.Y` |
| **Run** | `.venv/Scripts/python main_script.py [args]` |
| **Status** | (active / v1 complete / in development / deprecated) |
```

Optional fields when relevant:
- **Key functions** — for libraries the operator imports rather than CLI scripts.
- **Security** — special handling notes if the tool touches sensitive data.
- **Commands** — for tools with subcommands (`run.py report`, `run.py sync`, etc.).
- **External dependencies** — services, APIs, or hardware the tool needs.

## Suggested structure

Group tools by audience and tier:

```markdown
## 1. Client/Customer-Facing Tools (Tier 1)
   1.1 [tool]
   1.2 [tool]
   ...

## 2. Internal Tools (Tier 1)
   2.1 [tool]
   ...

## 3. Tier 2 Tools (e.g. community engagement / content)
   3.1 [tool]
   ...

## 4. Databases
   (one row per durable database file with schema summary + size)

## 5. Generated Documents (Outputs)
   (one row per typical generated artifact: doc, report, deliverable)

## 6. Reference Data (Read-Only)
   (pointers — full detail in `DATA_SOURCES.md`)

## 7. Governance & Documentation Files
   (DIRECTIVE, GOVERNANCE, FOLDER_LAYOUT, etc.)

## 8. Research / No Code Yet
   (planned tools — clearly marked as not built)

## 9. Python (or your language) Environments
   (one row per venv with location, tools served, key pinned versions)

## 10. Infrastructure
   (servers, sync providers, monitoring, CI)

## 11. Tier 3 — Creative Projects
   (separate to keep Tier 1/2 working areas tight)
```

## Per-tool README pattern

For non-trivial tools, the inventory entry points at a per-tool
`README.md` in the tool's directory that goes deeper:

```
Tools/Quote_Generator/
├── .venv/
├── requirements.txt
├── MAINTENANCE_LOG.md         ← decisions / errors / handoff
├── README.md                  ← user guide (one-page max)
├── build_quote.py
└── output/
```

Inventory says *what it is*. README says *how to run it from cold
start*. MAINTENANCE_LOG says *why it works the way it does*.

---

## What NOT to put here

- **Conversation context.** → `MEMORY.md` topic files.
- **Per-tool decision history.** → that tool's `MAINTENANCE_LOG.md`.
- **External data sources.** → `DATA_SOURCES.md`.
- **Active task status.** → `TASK_QUEUE.md`. Inventory says "the tool
  exists." Task queue says "we're working on it today."

---

## Anti-patterns

**The wishlist.** Listing tools that don't exist yet as if they do.
Use Section 8 (Research / No Code Yet) and label clearly.

**The marketing description.** "This sophisticated tool leverages..."
No. State what the tool does. One sentence. Move on.

**The stale inventory.** A tool was renamed, moved, or deleted, and
inventory still references the old path. Worse than no inventory —
it actively misdirects. Update during the session that makes the
change.

---

## Maintenance

- **At end-of-session:** if a tool was created, modified, or removed,
  update the inventory entry.
- **Monthly cadence** (in `SESSION_ENV.md` checklist): scan the
  inventory, spot-check three random entries against actual file
  state. Catch drift.
- **Quarterly:** trim deprecated entries; promote planned-tools
  (Section 8) into their proper section if they got built.
