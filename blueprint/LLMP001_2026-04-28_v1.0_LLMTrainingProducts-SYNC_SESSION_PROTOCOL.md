> **Purpose.** Define the routine the agent runs at the start and end
> of every session — what it reads, what it updates, what it surfaces
> to the operator. This is what turns "a clever assistant" into "a
> colleague that picks up where we left off."

---

## Why a protocol at all

Without a protocol, every session starts from the agent's defaults.
Defaults are: re-introduce, re-explain, re-discover. That's the
groundhog-day problem. A start-of-session protocol burns 30 seconds
to load context that would otherwise take 10 minutes to rebuild
through conversation.

Without an end-of-session protocol, decisions made today don't
propagate to tomorrow. You re-explain. You re-decide. The system
decays.

The protocol is short. It is also non-negotiable — its value comes
from being *automatic*, not from being elaborate.

## Start of session — 8 steps

The agent runs through these in order at the start of every session,
unannounced. The operator should not have to ask.

### 1. Read the directive

`DIRECTIVE.md` (or `CLAUDE.md`, or whatever your harness's auto-load
file is named). The contract that anchors the session.

If the directive is auto-loaded by your harness, this step is free.
If not, the agent reads it explicitly before doing anything else.

### 2. Read memory index

`MEMORY.md` from the auto-memory directory. Index of all topic
files. Note what's in scope; don't load topic files yet.

### 3. Load relevant topic files

Based on the operator's first message, load any topic files whose
descriptions match the work at hand. Don't load everything — that
defeats the index.

### 4. Read TASK_QUEUE

`TASK_QUEUE.md`. What's open, what's in progress, what's blocked.
Get a one-paragraph mental picture of the current work landscape.

### 5. Read SESSION_ENV recurring-maintenance checklist

`SESSION_ENV.md` has a recurring-maintenance checklist with cadence
dates. Surface anything overdue: security scan due, memory index
review due, task-queue stale-item check due. Don't *do* the
maintenance; just surface it so the operator can decide.

### 6. Confirm what's next

Restate to the operator: "Based on `TASK_QUEUE.md`, [task X] is in
progress. [Maintenance item Y] is overdue. Do you want to continue
[X], handle [Y], or pivot?"

This is the operator's chance to redirect. Common responses:
- "Continue [X]" — agent proceeds.
- "Pivot to [new ask]" — agent updates its mental model.
- "Handle [Y] first" — agent runs the maintenance task.

### 7. Resolve open conflicts before acting

If memory says one thing and the current code/state says another,
flag the conflict before proceeding. Don't act on stale memory. Trust
what's observable now and surface the discrepancy for resolution.

### 8. Begin the work

Only after steps 1-7 land. Don't shortcut by jumping straight to the
operator's request.

## During session — standing rules

Three rules that stay active throughout.

### Plain-language proposal before code

For any task estimated >5 minutes: brief the operator first. Scope,
approach, success criteria, estimated time. Wait for approval. *Then*
execute.

This catches bad plans before implementation. Cheap insurance.

### When something fails twice, flag and propose alternatives

Don't iterate on a broken approach indefinitely. Two failures = stop,
explain what's not working, propose two or three different paths,
let the operator pick.

### Three gates before acting on memory

1. **Ask gate.** When the operator explicitly asks for a recollection,
   verify against current state before answering.
2. **Save gate.** Before saving a memory based on inferred state,
   confirm the inference matches reality.
3. **Cold-read gate.** When loading a topic file, scan it against
   current evidence; don't blindly cite outdated content.

These three gates are the standing defense against context drift
(see `KNOWN_LIMITATIONS.md` §3).

## End of session — 5 steps

Run before the operator wraps up. Don't skip. The whole point is to
make tomorrow's session start hot.

### 1. Update MEMORY topic files

Anything new learned this session that fits one of the four memory
types (user, feedback, project, reference): write or update the
topic file. Update the index pointer.

Don't dump conversation summary into memory. Capture *durable*
facts only.

### 2. Update TASK_QUEUE

Move tasks: `[ ]` → `[>]` (started) → `[x]` (done) → `[~]` (blocked,
note why). Add new tasks discovered this session.

### 3. Update SESSION_ENV log

Add a context-evolution entry: what changed today, why, lessons.
Update last-run dates on any maintenance items completed.

The entry should be skimmable in 60 seconds: 4-6 bullets max.

### 4. Update per-tool MAINTENANCE_LOG

For any tool touched this session: add to its `MAINTENANCE_LOG.md`.
Error log entries (if anything broke), reasoning for non-trivial
choices, dependency changes, handoff notes.

### 5. Confirm clean state

Before sign-off: any background tasks running? Any unsaved files?
Any unfinished writes? Surface them. Don't sign off with state in
flight.

## What "session start hot" looks like

After a good end-of-session protocol, tomorrow's session begins:

- Agent loads directive (auto).
- Reads MEMORY.md — sees yesterday's "in progress" memory.
- Loads relevant topic files for that work.
- Reads TASK_QUEUE — sees the `[>]` item from yesterday.
- Reads SESSION_ENV — sees yesterday's evolution log.
- Says: "Yesterday we were on [X], status [Y]. Maintenance item [Z]
  is overdue. Continue [X]?"

Total time: ~60 seconds. The operator picks up exactly where they
left off, no re-briefing.

## What breaks the protocol

These are the failure modes. Watch for them.

- **Skipping end-of-session.** "I'll do it tomorrow." Tomorrow you
  don't remember. Memory falls behind. Pattern decays.
- **Index bloat.** `MEMORY.md` over 200 lines stops auto-loading
  fully. Curate ruthlessly.
- **Vague entries.** "Worked on X" tells future-you nothing. Write
  for someone who wasn't here.
- **Dumping conversation summary into memory.** Memory is for
  *durable* facts, not session transcripts.
- **Letting maintenance items slip past their cadence.** The
  checklist exists because willpower fails. Honor it.

## Per-harness adaptation

The protocol above is harness-agnostic. Specific harnesses may auto-
load some of these files for you:

| Harness | Auto-loaded |
|---|---|
| Claude Code | `CLAUDE.md` and `MEMORY.md` index |
| Cursor / Cline | varies — check your config |
| Custom agent | whatever your loader does |

If your harness auto-loads, the agent doesn't need to "read" those
files explicitly — they're already in context. The protocol still
applies; it's just that some steps become free.
